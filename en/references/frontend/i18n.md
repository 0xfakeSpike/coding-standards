# Internationalization

This document covers UI text management, plurals, dates and currency, time zones, RTL, and text length. For `hreflang`, see [html.md](html.md). The rules on date formats, time zones, and number formats also apply to single-language projects.

## UI text management

### Do not hard-code UI text [Recommended]

In projects that need translation, all UI text goes through message files or a message API, including `aria-label`, `alt`, and `placeholder`.

**Tooling:** `formatjs/no-literal-string-in-jsx`.

**Source:** FormatJS Docs

### Make each message a complete sentence [Recommended]

Do not build sentences by string concatenation. When values are known at development time, write multiple complete messages. Use interpolation only for values known only at runtime, such as user names and times.

**Why:** Word order and word forms vary by language, and translators cannot adjust fragments assembled in code.

**Example:**

Avoid:

```ts
const text = t('deleted') + count + t('files');
```

Prefer:

```ts
const text = t('files_deleted', { count });
```

**Tooling:** `formatjs/prefer-full-sentence`.

**Source:** ICU Message Format Docs, i18next Docs

### Use meaningful keys and parameters, and provide context [Recommended]

Keys state purpose, such as `checkout.submit`. Do not use the source text as the key. Parameters use names such as `{guestCount}`, not `{0}`. FormatJS projects write `defaultMessage` and `description` where the message is used.

**Tooling:** `formatjs/enforce-description`, `formatjs/no-invalid-icu`.

**Source:** i18next Docs, FormatJS Docs, ICU Message Format Docs

### Do not disable interpolation escaping [Required]

i18next escapes interpolation by default. Do not use `escapeValue: false` or `{{- value}}` for user input. When you truly must disable it, escape the values yourself. For security requirements, see [security.md](security.md).

**Source:** i18next Docs

### Use BCP 47 language tags [Recommended]

Add a region only when you need the distinction, such as `en-GB`. On first visit, choose with `Accept-Language`, not by inferring from IP.

**Source:** W3C: Language Negotiation, W3C: Language Tags, MDN

## ICU plurals

### Use message syntax for plurals, not conditional branches [Recommended]

Use ICU `plural`. The `other` branch is mandatory, and numbers use `#`. Use `=0` only when customizing for one exact value. Do not use `=1` in place of `one`, because in some languages `one` covers more than 1. Use `selectordinal` for ordinals. The ASCII single quote is the escape character, so use `’` for apostrophes in displayed text.

**Why:** Plural categories differ by language. English has two, Arabic has six, and Chinese has only `other`. `count === 1` in code holds only for some languages.

**Example:**

```text
{count, plural, =0 {No files} one {# file} other {# files}}
```

**Tooling:** `formatjs/enforce-plural-rules`, `formatjs/prefer-pound-in-plural`.

**Source:** FormatJS Docs, ICU Message Format Docs, MDN

### Put `select` outside and `plural` inside [Recommended]

Write a complete sentence in each branch, and avoid nesting beyond one level.

**Tooling:** `formatjs/no-multiple-plurals`.

**Source:** ICU Message Format Docs

### Express plurals with suffixes in i18next [Required]

Keys use CLDR suffixes such as `file_one` and `file_other`, and calls must pass a parameter named `count`. Without it, lookup does not fall back to the base key.

**Source:** i18next Docs

## Dates and currency

### Keep one date format and format centrally [Required]

The project has one date formatting module, with named presets inside, and business code passes only the preset name. Do not write `toLocaleDateString()` or format strings in components. Cache and reuse `Intl.DateTimeFormat` instances by language, time zone, and preset.

**Why:** Multiple formats eventually diverge. Repeated `toLocaleDateString` calls look up locale data each time, which costs more.

**Example:**

Avoid:

```tsx
<td>{new Date(order.createdAt).toLocaleDateString('zh-CN')}</td>
```

Prefer:

```tsx
<td>{formatDate(order.createdAt, 'dateTime')}</td>
```

**Source:** Team, MDN

### Use `Intl.NumberFormat` for numbers and currency [Recommended]

Do not hand-write thousands separators or concatenate currency symbols. State the ISO 4217 code for currency. The code comes from data and is not inferred from language. When an API amount is in the minor currency unit, first convert it by the currency's decimal places, which differ by currency. This also lives in the formatting module.

**Example:**

```ts
new Intl.NumberFormat(locale, { style: 'currency', currency }).format(amount);
```

**Source:** MDN

### Use `Intl` for other localized output too [Recommended]

Use `Intl.RelativeTimeFormat` for relative time, `Intl.ListFormat` for lists, and `Intl.Collator` for sorting user-visible text. Tests and logic do not compare against hard-coded formatted strings. When you need one part of the output, use `formatToParts()`.

**Why:** Output varies by implementation, language, and version.

**Source:** MDN

## Time zones

### Distinguish instants from local dates [Required]

Transmit instants such as order time in UTC, with `Z` in the string. Also accept valid offsets when parsing, and convert for display. Handle local dates such as birthdays and holidays as `YYYY-MM-DD`. Do not convert them to `Date` and then display them in the local time zone. Do not parse formats other than ISO 8601, because their behavior is implementation-defined.

**Why:** `new Date('2026-03-01')` parses as UTC, so it displays as the previous day in time zones west of UTC. A date-time without an offset, by contrast, parses as local time.

**Source:** W3C: Time Zones, MDN

### Specify the time zone in server-side rendering [Required]

Time formatting during server-side rendering must pass `timeZone`, taken from the user's setting or the business location. Do not rely on the runtime's default time zone. Pure client-side rendering may use the browser time zone. When the business requires a fixed time zone, pass it there too.

**Why:** The default is the runtime's time zone, which may differ between server and browser, so render results do not match.

**Source:** MDN

### Store IANA time zones for future events [Recommended]

For appointments and recurring events, store the local time and a time zone ID such as `Asia/Shanghai`, not just an offset. Do not assume a day is always 24 hours.

**Why:** Daylight saving and time zone rules can change, and an offset alone miscalculates future local times.

**Source:** W3C: Time Zones

## RTL

### Set direction in HTML [Recommended]

RTL pages write `dir="rtl"` on `<html>`, along with `lang`. Do not set page direction with the CSS `direction` property. Language does not determine direction either.

**Why:** Direction is part of the content's meaning and must survive when stylesheets are unavailable.

**Source:** W3C: Text Direction

### Use logical properties instead of left and right [Recommended]

Use `margin-inline-start`, `padding-inline`, `inset-inline-end`, and `text-align: start` instead of properties such as `margin-left`. In Tailwind, use `ms-*` and `me-*`. For projects that need RTL support, this rule is [Required].

**Why:** The same styles flip with `dir`, with no separate RTL stylesheet.

**Source:** MDN, web.dev Learn CSS, W3C: Text Direction, Tailwind CSS Docs

### Isolate text of unknown direction [Recommended]

Wrap content inserted into sentences, such as user names, in `<bdi>`. Use `dir="auto"` for user-entered content and input fields. Flip directional icons such as back arrows in RTL. Do not flip logos.

**Why:** In mixed text, inserted text can scramble the surrounding order. `dir="auto"` looks only at the first strong directional character and is not always accurate.

**Source:** W3C: Text Direction

## Text length

### Leave layout room for translation growth [Recommended]

Text containers use flexible layout without hard-coded width or height. Buttons and labels may wrap or expand. Short text grows the most: when English is translated into European languages, text up to 10 characters can reach 200% to 300%, and text over 70 characters about 130%. Chinese source text is compact and usually gets longer in other languages.

**Why:** Buttons sized to the width of Chinese text easily overflow or truncate once translated.

**Source:** W3C: Text Length

### Account for different scripts [Recommended]

Long compound words in languages such as German do not wrap easily, so you may use CSS `hyphens`. Languages such as Thai and Arabic need larger line height, so do not hard-code line height. Check truncation and alignment with pseudo-translation or the longest target language.

**Source:** W3C: Text Length, web.dev Learn Design
