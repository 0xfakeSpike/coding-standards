# Consistency

This document defines how to decide state from facts and keep data correct under concurrency and in distributed environments. For transaction details, see [Transactions](../data/transactions.md). For message delivery, see [Messaging](../async/messaging.md).

## Decide from factual data

### Keep decision logic close to the facts [Required]

Decide state from actual data, for example by comparing timestamps to see which is newer, or skipping processing when the target already has the data. Do not infer it from indirect flags.

**Why:** A flag is only a restatement of the facts. Interrupted writes, manual data fixes, or concurrency can all put a flag out of step with the actual data, while decisions keep relying on the wrong flag.

**Example:**

Avoid:

```sql
SELECT id FROM source_items WHERE synced = false;
```

Prefer:

```sql
INSERT INTO target_items (id, payload, updated_at)
VALUES (:id, :payload, :updated_at)
ON CONFLICT (id) DO UPDATE
SET payload = EXCLUDED.payload, updated_at = EXCLUDED.updated_at
WHERE target_items.updated_at < EXCLUDED.updated_at;
```

**Source:** Team

### Take compared timestamps from one authoritative source [Required]

When comparing which is newer, the data's owner generates the timestamp. Do not mix local clocks from different machines. When strict ordering is needed, use an increasing sequence number generated by the owner.

**Why:** Clocks on different machines can disagree or even jump backward.

**Source:** Kleppmann: Distributed Locking

## Idempotency

For request identifiers on critical write operations, see [rest.md](../api/rest.md).

### Make operations with side effects idempotent [Required]

For write operations that may be retried, replayed, or delivered more than once, running them several times has the same effect as running them once.

**Why:** A timeout does not mean the other side did not execute, and messages are usually delivered at least once. Duplicates are normal.

**Source:** AWS: Timeouts and Retries, Azure: Idempotent Consumer

### Prefer the data itself for idempotency [Recommended]

When a unique constraint, a conditional update, or "skip if the target already has it" can do the job, do not maintain separate deduplication records.

### Return results with the same meaning for duplicate requests [Recommended]

When you detect a duplicate, return a response with the same meaning as the first success. Do not return an error such as "already exists". The same identifier with different parameters is not a duplicate, so store the parameters or a digest of them along with the identifier. For API-level responses, see [rest.md](../api/rest.md).

**Source:** AWS: Idempotent APIs

### Write deduplication records in the same transaction as business data [Required]

When a deduplication table is truly needed, commit the identifier and the business data in the same transaction. If they commit separately, a crash causes lost or duplicate processing. When multiple consumers share a deduplication table, the key must include the consumer identity.

Use a stable business identifier or a producer-assigned message identifier as the deduplication key, not a correlation ID.

**Source:** Azure: Idempotent Consumer

## Concurrency control

Do not call external services inside a transaction. See [Transactions](../data/transactions.md).

### Do not use "check then write" to guarantee uniqueness [Required]

Two concurrent requests can both pass the check. Use a database unique constraint, a conditional update, or a lock.

**Example:**

Avoid:

```sql
SELECT count(*) FROM users WHERE email = :email;
INSERT INTO users (email) VALUES (:email);
```

Prefer:

```sql
ALTER TABLE users ADD CONSTRAINT uk_users_email UNIQUE (email);
INSERT INTO users (email) VALUES (:email);
```

### Choose concurrency control by conflict frequency [Recommended]

| Method | Use when | Notes |
|---|---|---|
| Conditional update | Simple single-row changes | First choice, judge the result by affected rows |
| Optimistic lock (version number) | Long gap between read and write, few conflicts | On conflict, reread and then decide |
| Pessimistic lock | Many conflicts, high cost to redo | Hold locks briefly, use a fixed lock order |
| Distributed lock | Coordinating across data sources | Last resort |

**Example:**

```sql
UPDATE inventory SET stock = stock - 1
WHERE sku_id = :sku_id AND stock >= 1;
```

## Distributed locks

### Confirm what the lock is for first [Recommended]

| Purpose | Consequence of lock failure | Requirement |
|---|---|---|
| Efficiency, avoiding duplicate work | Work done one extra time, low cost | A simple implementation is enough |
| Correctness | Data corruption | Must have protection at the storage layer |

When a unique constraint or conditional update can solve it, do not introduce a distributed lock.

**Source:** Kleppmann: Distributed Locking

### Set an expiry and release only locks you hold [Required]

Locks must have an expiry so a crashed holder cannot hold one forever. When locking, write a random value identifying the holder. When releasing, compare and delete atomically so you do not delete someone else's lock.

### A lock is not the only guarantee of correctness [Required]

During a process pause or network delay, the holder may resume writing after the lock has expired. By then, another party already has the lock.

When correctness depends on a lock, writes carry an increasing fencing token, and storage rejects smaller tokens. Database constraints are the last line of defense.

**Source:** Kleppmann: Distributed Locking

## Outbox

The relay can crash after sending and before recording, so messages can be duplicated. For consumer idempotency, see [Messaging](../async/messaging.md). Polling is the simplest way to implement a relay.

### Use Outbox when message loss is unacceptable [Recommended]

By default, send directly after the transaction commits, and state that messages may be lost if the process crashes. When message loss is unacceptable, tell the user first, then use Outbox: write business data and pending messages in the same transaction, and let a separate relay process deliver them. Never send inside a transaction.

**Why:** If you send inside a transaction, the message has already gone out when the transaction rolls back. If you send after commit, a process crash loses the message.

**Example:**

```sql
BEGIN;
UPDATE orders SET status = 'paid' WHERE id = :id AND status = 'pending';
INSERT INTO outbox (id, topic, payload, created_at)
VALUES (:event_id, 'order.paid', :payload, :now);
COMMIT;
```

**Source:** microservices.io Outbox

## Saga

### Prefer avoiding cross-service transactions [Recommended]

When you need a Saga, check the service boundaries first. Strongly consistent data usually belongs in the same service. See [Service boundaries](../architecture/service-boundaries.md).

A Saga splits a business operation into multiple local transactions. When a step fails, compensating operations undo the earlier steps. Compensation targets failures that occur normally in the business, such as insufficient stock. Do not add compensation for rare technical failures. See [Resilience](resilience.md).

**Source:** Azure: Microservice Boundaries, Azure Saga

### Choose the coordination style by step count [Recommended]

| Style | Use when | Risk |
|---|---|---|
| Choreography (event-driven) | Few steps, few participants | Flow is scattered, hard to trace, possible cyclic dependencies |
| Orchestration (central coordinator) | Many steps, complex flow | The coordinator is a new point of failure |

**Source:** Azure Saga

### Put irreversible steps late [Recommended]

Steps fall into three types: compensable, irreversible pivot steps, and retryable steps after the pivot. Once the pivot step succeeds, later steps cannot be undone, only retried, so they must be idempotent. When retries are exhausted, alert and handle manually.

**Source:** Azure Saga

### Handle the Saga's lack of isolation [Required]

Local transactions have already committed, so other flows can see intermediate state, and lost updates and dirty reads can occur. Mark intermediate state with a business status such as "processing", and reread to confirm before updating. Compensation itself can also fail, so have alerts and a way to handle it.

**Source:** Azure Saga

## Eventual consistency

### State the acceptable delay [Recommended]

When using eventual consistency, write down the longest time until data is consistent and what users see during the inconsistency, and monitor the actual delay. While async processing is unfinished, show "processing", not success.

### Consumers accept out-of-order messages [Recommended]

Do not depend on ordering when you can avoid it. When older data arrives, compare as in "Keep decision logic close to the facts" and skip it.

**Source:** Azure: Queue-Based Load Leveling
