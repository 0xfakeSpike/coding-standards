# 配置

本文规定配置的来源、校验、动态调整、功能开关和密钥边界。容器层面的配置注入见 [容器](../../general/containers.md)。

## 配置分层

### 配置与代码分离 【必须】

随部署环境变化的值都是配置，比如数据库地址、外部服务地址和凭据。这些值通过环境变量或配置中心提供，不写在代码里。

不随部署变化的内部连接关系，比如路由表和依赖组装，不算配置，留在代码中。

**原因：** 配置写在代码里，换环境就要改代码，凭据也会进入版本库。

**示例：** 判断标准是，把代码库立刻公开时，不会泄露任何凭据。

**来源：** Twelve-Factor App

### 按优先级合并配置来源 【推荐】

| 优先级 | 来源 | 内容 |
|---|---|---|
| 高 | 运行时动态配置 | 需要不重启调整的值 |
| 中 | 环境变量或部署平台注入 | 每次部署的差异 |
| 低 | 代码内默认值 | 所有环境都合理的安全默认值 |

优先级在项目内统一，并写入项目文档。不把配置来源散落在业务代码中，读取集中在一处，业务代码接收已解析好的配置对象。

### 不按环境名分组配置 【推荐】

不写 `if env == "production"` 这类分支，也不维护一组组按环境命名的配置集合。每个配置项独立设置。

**原因：** 环境增多后，组合数量失控，也容易出现只有某个环境才有的行为。

**示例：**

反例：

```json
{
  "production": { "timeoutMs": 2000, "retry": true },
  "staging": { "timeoutMs": 5000, "retry": false }
}
```

正例：

```text
PAYMENT_TIMEOUT_MS=2000
PAYMENT_RETRY_ENABLED=true
```

**来源：** Twelve-Factor App

### 提交配置样例 【推荐】

提交 `.env.example`，只放变量名和示例值，不放真实值。新增配置项时同步更新，并写明含义和单位。

### 配置项名字带单位 【推荐】

时长、大小类配置在名字中写明单位，比如 `REQUEST_TIMEOUT_MS`、`MAX_UPLOAD_BYTES`。

## 校验

### 启动时校验，缺失时立即失败 【必须】

服务启动时校验所有配置的存在性、类型和取值范围。校验失败就退出，并写明哪一项有问题，错误信息不输出配置值本身。

**原因：** 问题留到运行时才暴露，往往要等某条低频路径执行才发现，而那时流量已经进来了。

**示例：**

反例：

```text
服务启动成功，第一笔支付时才报错：payment url is empty
```

正例：

```text
启动失败：PAYMENT_TIMEOUT_MS 必须是正整数，当前值不合法
```

### 必需配置不给默认值 【必须】

数据库地址、凭据这类必需项没有合理默认值时，不写占位默认值。默认值指向本地地址时，配置遗漏会变成错误连接，而不是启动失败。

### 默认值要安全 【必须】

有默认值的配置项，默认值选更保守的一侧，比如调试模式默认关闭、校验默认开启。

## 动态配置

### 只有确实需要才做成动态配置 【推荐】

能随部署发布的配置就不做成动态配置。需要动态调整的通常是事故时要快速改的值，比如限流阈值和运维开关。

**原因：** 静态配置随代码一起评审和回滚，动态配置多一套分发系统，也多一种线上状态。

**来源：** Fowler 功能开关、Azure 节流

### 动态配置更新前校验 【必须】

新值先校验再生效。校验失败时保留当前值并告警，不让进程带着非法配置运行。

### 配置中心不可用时继续运行 【必须】

**适用：** 线上服务

服务启动后，配置存储不可用不影响运行，继续使用内存中的最后一份有效配置。配置读取要缓存，不在每次请求时远程读取。

**来源：** Azure 外部配置存储

### 动态配置的修改要留痕 【推荐】

**适用：** 线上服务

记录谁在什么时间把什么值改成了什么，并设置访问权限。配置变更和发布一样可能引发故障，排障时要能对上时间。

**来源：** Azure 外部配置存储

### 启动时记录生效配置 【推荐】

启动时输出非敏感配置的摘要，便于确认线上实际运行的配置。敏感项只输出是否已设置。

## 功能开关

### 新旧切换用的开关，切换完成后删除 【必须】

为新旧切换引入的功能开关是临时的。切换完成后，开关和旧路径一起删除。开关的类型、负责人和删除日期见 [发布与回滚](../../general/release.md)。

**原因：** 残留的开关会让人不知道哪条路径在运行，分支组合也会持续增加测试成本。

**来源：** 团队

### 开关和配置分开看待 【推荐】

| 类型 | 生命周期 | 存放位置 |
|---|---|---|
| 发布开关 | 短期，用完删除 | 静态配置优先 |
| 运维开关 | 按需长期保留 | 动态配置 |
| 普通配置 | 长期 | 配置来源 |

开关是有持有成本的库存，数量越少越好。

**来源：** Fowler 功能开关

### 开关状态可查 【推荐】

提供查询当前开关状态的方式，比如管理接口或启动日志。排障时要能知道某个实例走的是哪条路径。

**来源：** Fowler 功能开关

## 密钥边界

打印配置和校验错误时，敏感项要脱敏，见 [日志](../observability/logging.md)。

密钥不进代码、镜像和普通配置，见 [加密与密钥](../security/crypto-and-secrets.md)。

### 优先运行时获取或文件挂载 【推荐】

能用密钥管理服务或挂载文件时优先使用。环境变量对同容器的进程可见，也可能进入日志和转储，是其他方式都不可行时的选择。

**来源：** OWASP 机密管理速查表
