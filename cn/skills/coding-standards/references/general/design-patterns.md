# 设计模式

本文讲什么时候该用设计模式、选哪一种、写成多轻的形态。改动放在哪里、要不要封装见 [code-design.md](code-design.md)，模块边界见 [responsibilities.md](responsibilities.md)。

代码读起来绕，常见原因不是细节没写好，而是缺了合适的结构：本该查表的写成一长串条件，本该是状态机的散成几个布尔值，本该是管道的写成层层嵌套。这时加注释、拆小函数都解决不了，要换结构。反过来，没有问题时硬套模式，同样会让代码绕。

## 使用原则

### 代码绕时先找缺的结构 【必须】

写代码或审查时，如果一段代码要来回跳着读、要靠注释才说得清，先对照下面的信号速查表找出它缺的结构，再决定怎么改。不靠加注释、加判断或机械地拆小函数来缓解。

**判断信号：**

- 同一组按类型或状态的分支在多处重复出现。
- 新增一种类型或一个步骤，要改好几处判断。
- 读懂一个函数需要同时记住几个标志变量的组合，或者要靠一串条件推断现在走到了哪一步。
- 主流程被前置检查、日志、重试这类与业务无关的代码淹没。

**来源：** 团队

### 模式要换来实际收益 【推荐】

模式用来解决已经出现的问题，不用来证明设计“规范”。引入时要能说出它减少了什么：更少的重复分支、更集中的规则，或者新增一种类型时只改一处。说不出来就不用。

**判断标准：** 去掉这个模式后，代码是否更难读或更难改。不会就删掉。

**常见反例：**

- 只有一个实现、也没有替换需求的策略接口。
- 只创建一种对象的工厂。
- 什么也没加的装饰器或代理。
- 只有一个接收方、发起方本来就知道它是谁的事件。

### 选最轻的形态 【推荐】

同一个模式有轻重不同的写法，按这个顺序选：数据（查表）、函数、带方法的类型、类层次。前一种能表达清楚就不用后一种。

**示例：** 按支付渠道计算手续费，一张“渠道 → 计算函数”的表就够了，不需要 `FeeStrategy` 接口、每个渠道一个类，再加一个工厂。某个渠道需要自己的状态和多个方法时，再把它升级为类型。

### 不照搬 Java 式的模式结构 【必须】

模式落到代码时，用所在语言的惯用形态。TypeScript、Python 和 Go 都有一等函数、模块和闭包，教科书里为 Java 设计的类结构，在这些语言里大多是多余的层次。各语言的对应写法见语言层的 `patterns.md`。

**判断信号：**

- 只有一个实现的接口，或者 `IUserService` 加 `UserServiceImpl` 这样的成对命名。
- 一个策略配一个接口、一个抽象基类、每种情况一个类，再加一个工厂或注册表。
- 用 `getInstance()` 实现的单例。
- 只装静态方法的 `Utils`、`Helper`、`Manager` 类。
- 只转发字段的 getter 和 setter。
- 为复用几行代码建的抽象基类和继承层次。
- 给只有几个字段的对象写建造者。

**原因：** 每多一层类结构，读者就要多跳转一次，而这些层次在这些语言里不带来额外的保证。

**来源：** 团队

### 引入模式时一次迁移完 【推荐】

用新结构替换旧写法时，把所有旧分支都迁移过去，删掉旧写法，不让新旧两套并存。

**原因：** 两套并存时，读者要先判断该看哪一套，新需求也不知道该加在哪里，见 [responsibilities.md](responsibilities.md) 的“同一件事只留一份”。

## 信号速查

| 信号 | 先考虑 | 最轻形态 |
|---|---|---|
| 一串条件只是把一个键映射成值或处理函数 | 查表 | 字典或映射 |
| 同一个类型字段的分支出现在多处，而且类型在增加 | 按类型组织行为（策略、多态） | 每种类型一个函数，放进映射 |
| 类型固定，要对它们做的操作在增加 | 每种操作一个穷尽的分支（访问者） | 每种操作一个函数，内部按类型 `switch` |
| 几个布尔值或可空字段拼出一个状态，或一串 `if` 推断现在走到哪一步 | 状态机 | 一个状态字段，加迁移表或按状态 `switch` |
| 请求要依次过多个步骤，每步都可能提前结束 | 管道、中间件（责任链） | 签名相同的函数列表 |
| 两段流程只有一两步不同 | 把不同的步骤传进来（模板方法） | 接收函数参数的流程函数 |
| 日志、计时、重试、权限检查复制在多个函数里 | 装饰器、中间件 | 包装函数 |
| 业务代码到处处理第三方的字段和格式 | 适配器 | 边界上的一个转换函数 |
| 按条件创建不同实现的代码散在各处 | 工厂 | 入口处的一个创建函数 |
| 一个动作完成后，发起方逐个调用无关的模块 | 观察者、事件 | 回调列表或领域事件 |
| 操作需要排队、撤销、重放或审计 | 命令 | 把操作表示成数据 |
| 树形结构对单个节点和整组节点分别处理 | 组合 | 节点和整组实现同一套操作 |
| 调用处传一串含义不明的可选参数 | 配置对象 | 具名参数或配置结构 |
| 同一个值在多处判空 | 空对象、默认值 | 边界上的默认值或空实现 |

速查表给的是“先考虑”，不是“必须用”。每次都按“模式要换来实际收益”复核一遍。

## 分支

### 值映射用表，不用条件链 【推荐】

条件链只是把一个键映射成值或处理函数时，写成一张表。加一项只改一行，测试也能遍历整张表。

各分支里是各不相同的复杂逻辑时，不硬塞进表。

**示例：** 根据错误码返回提示文案，写成“错误码 → 文案”的映射，查不到时走一个默认值，不写二十个 `if`。

### 按类型的分支多处重复时，看增加的是类型还是操作 【推荐】

同一个类型字段的判断出现在两处以上时，先看以后增加的是哪一边：

- **类型在增加，操作基本固定：** 每加一种类型都要改这些分支。把每种类型的行为放在一起，每种类型一组函数，或者一个接口加各自的实现。判断类型只留在解析或创建的一处。
- **类型固定，操作在增加：** 每种操作写一个函数，内部按类型 `switch` 并让分支穷尽。加操作只新写一个函数，类型偶尔增加时由编译器或 lint 指出所有漏处理的地方。不改成多态，也不写访问者类。

只有一处分支、每个分支都很短时，保留 `switch`，并让分支穷尽。

**示例：** 会员等级经常调整，计价、展示文案和退款规则都按等级分支，每加一个等级要改三处。改成每个等级一组“计价、文案、退款”，加等级只加一组。

**示例：** 消息只有文本、图片、文件三种，很少变化，但要做的校验、渲染、导出、审核越来越多。每种操作一个函数，里面按消息类型 `switch`。

### 到处判空时，在边界补上默认值或空实现 【推荐】

同一个值在多处判空时，在它进入业务代码的地方一次处理：可选的配置给默认值，可选的依赖给一个什么都不做的实现，比如不输出的 logger、不发送的通知器。后面的代码不再判空。

只有“缺失”本身合法时才这样做。值本来不该为空时，按 [principles.md](principles.md) 的“不打补丁”查清为什么为空，不用默认值掩盖。默认值不能放宽安全限制，见 [configuration.md](../backend/architecture/configuration.md) 的“默认值要安全”。

## 状态

### 状态靠标志或条件推断时用状态机 【推荐】

出现下面任一情况，说明缺了状态机：

- 一个对象的生命周期用多个布尔值或可空字段拼出来（`isPaid`、`isShipped`、`canceledAt`），会出现非法组合，判断条件也散在各处。
- 过程式代码用一串 `if` 推断现在走到了哪一步，读者要把所有条件拼起来才知道流程，每加一步都要改前面的条件。

改成一个显式的状态字段，再按情况选写法：

- **迁移表：** 状态之间只是“当前状态加事件，得到下一个状态”的映射时，把允许的迁移列成表。
- **按状态 `switch`：** 每个状态有自己的处理逻辑时，按状态 `switch`，每个 `case` 只处理一种状态，做完这一步的事后返回下一个状态。分支要穷尽，写法见语言层。

两种写法都只在一处执行迁移，非法迁移直接报错。

**示例：** 订单只允许在待支付时取消。迁移表里写一条“待支付 + 取消 → 已取消”，不在取消按钮、接口和定时任务里各写一遍 `!isShipped && !isCanceled`。

**示例：** 文件上传要经过取凭证、分片上传、合并、校验四步。过程式写法在每一步前用 `if (!token)`、`if (token && !uploaded)`、`if (uploaded && !merged)` 判断该做哪一步。改成状态“等待凭证、上传中、合并中、校验中、完成”，循环里按当前状态 `switch`，每个 `case` 只做这一步，然后返回下一个状态。

各语言的写法见语言层的 `patterns.md`，界面状态见前端的 [处理完整的 UI 状态](../frontend/components.md)。

## 流程

### 顺序步骤用管道或中间件 【推荐】

请求要依次经过校验、鉴权、限流、转换等步骤，每步都可能提前结束时，把每步写成签名相同的函数，按列表依次执行。主流程不再层层嵌套，增删步骤只改列表。

框架已经提供中间件或拦截器时，用框架的机制。

### 流程相同、个别步骤不同时，把不同的步骤传进来 【推荐】

两段流程只有一两步不同时，写一个流程函数，把不同的步骤作为参数传入。不复制整段流程再分别修改，也不用布尔参数在流程内部切换。

**示例：** 导出 CSV 和导出 Excel 都是“查询、过滤、格式化、上传”，只有格式化不同。写一个导出流程，接收格式化函数，不写两份几乎相同的导出函数。

### 横切逻辑用包装，不复制进每个函数 【推荐】

日志、计时、重试、缓存、权限检查这类与业务无关的逻辑在多个函数里重复时，写成包装函数、装饰器或中间件统一加上，业务函数里只留业务。

只在一两处出现时直接写在原处。重试本身的规则见 [resilience.md](../backend/reliability/resilience.md)。

## 边界与创建

### 外部格式在边界一次转换 【推荐】

第三方 SDK、外部接口和旧系统的数据，在边界用一个适配层转换成内部类型。业务代码只认内部类型，不在各处判断外部字段。更换供应商时只改适配层。

后端的做法见 [layering.md](../backend/architecture/layering.md) 的“用端口隔离外部世界”。

### 有选择逻辑的创建集中在一处 【推荐】

根据配置或输入决定创建哪种实现时，选择逻辑只写在一个创建函数里，通常放在程序入口或组装依赖的地方。业务代码拿到的是创建好的对象，不自己判断该创建哪种。

只有一种实现时直接创建，不加工厂。

## 通知

### 发起方不该认识接收方时用事件 【推荐】

一个动作完成后要通知多个模块，而这些模块与发起方的职责无关时，由发起方发布事件，接收方各自订阅。接收方自己决定何时处理，与 [responsibilities.md](responsibilities.md) 的“降低耦合”一致。发起方逐个调用接收方，会让它依赖的模块越来越多。

发起方需要知道结果，或者步骤之间有先后要求时，直接调用或显式编排，不用事件。跨模块的领域事件见 [domain-modeling.md](../backend/architecture/domain-modeling.md)。
