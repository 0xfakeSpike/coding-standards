# 重构

### 小问题也要改 【必须】

发现小问题就处理，不因为“不影响运行”而放过。当前任务范围外的问题按 [change-workflow.md](../collaboration/change-workflow.md) 先询问。

**来源：** 团队

### 重构与功能变更分开 【推荐】

**适用：** 多人协作

重构不改变行为，放在独立分支和 PR 中。

**原因：** 混在一起时，评审者无法判断行为变化是否有意为之。

**来源：** Google 评审规范

### 小步重构 【必须】

每一步都保持系统可运行，一次只解决一个问题。

**来源：** 团队

### 从结构入手 【推荐】

先看职责划分和数据模型是否合理，再优化函数内部写法。结构问题不解决，局部清理很快会失效。

### 没有测试时先保护行为 【推荐】

修改缺少测试的关键逻辑前，先写能记录当前行为的测试。

过时的测试见 [testing-strategy.md](testing-strategy.md) 的“过时测试直接删除”。

## 技术债

发现的技术债默认直接处理，方式见 [change-workflow.md](../collaboration/change-workflow.md) 的“发现问题要处理”。

### 留下的技术债要记录 【推荐】

确实不能马上处理时，按 [待办记入工单](project-docs.md) 记录，写清问题、影响和处理条件，不写在代码注释里。

## 代码坏味道

| 坏味道 | 常见处理 |
|---|---|
| 重复逻辑 | 收敛成一份 |
| 过长函数 | 按职责提取 |
| 过多参数 | 引入有含义的数据结构 |
| 只转调的函数 | 内联删除 |
| 永远走同一分支的条件 | 删除死分支 |
| 不再使用的配置 | 删除 |
| 需要解释才能看懂的代码 | 改命名和结构 |
