# Git 工作流

## 分支

### 从最新主分支开分支 【必须】

**适用：** 多人协作

新工作从最新的主分支开始。已合并的分支不再继续开发。

**来源：** 团队

### 一个分支一个问题 【必须】

**适用：** 多人协作

详见 [change-workflow.md](../collaboration/change-workflow.md) 的“分支尽快合入”。

**来源：** 团队

### 分支保持短期 【推荐】

短期分支只用于评审和 CI，尽快合回主干。未完成的功能可以用功能开关隐藏，不靠长期分支。

**来源：** Trunk Based Development、DORA 持续交付

### 分支命名 【推荐】

使用 `类型/简述`，有工单时带上工单号。

```text
feat/PROJ-123-order-export
fix/login-redirect-loop
```

### 保护主分支 【必须】

**适用：** 多人协作

不直接向主分支提交，通过 PR 合入，开启 CI 检查。

### 不对共享分支 force push 【必须】

这会覆盖他人的提交。个人分支需要改写历史时，使用 `--force-with-lease`。

## 提交

### 使用 Conventional Commits 【推荐】

```text
<type>(<scope>): <description>

<body>

<footer>
```

| type | 含义 |
|---|---|
| `feat` | 新功能，规范要求使用 |
| `fix` | 修复缺陷，规范要求使用 |
| `refactor` | 不改变行为的重构 |
| `perf` | 性能优化 |
| `test` | 测试 |
| `docs` | 文档 |
| `build`、`ci` | 构建和 CI |
| `chore` | 其他杂项 |

格式要求：

- type 后可带括号包裹的 scope，然后是冒号和空格。
- 正文与描述之间空一行。
- footer 与正文之间空一行，token 用 `-` 代替空格，比如 `Reviewed-by`。

**工具：** commitlint

**来源：** Conventional Commits

### 描述要说清改了什么 【推荐】

`fix bug`、`update`、`phase 1` 都不合格。首行是简短完整的描述，需要时在正文写明原因和背景。

**来源：** Google 评审规范

### 一个提交只做一件事 【推荐】

**适用：** 多人协作

无关清理和重构走独立分支和 PR，便于评审和回滚。独立提交只用于同一问题内部的拆分。

**来源：** Google 评审规范

## 提交内容

### 不提交敏感内容和构建产物 【必须】

包括密钥、本地环境配置、构建产物、依赖目录、IDE 个人配置和大体积二进制文件。代码生成物是否提交由项目统一决定。

### 泄露密钥后立即轮换 【必须】

删除文件或改写历史都不够，密钥可能已被拉取或缓存。

## 版本

### 使用语义化版本 【推荐】

格式为 `X.Y.Z`，打标签后该版本内容不再修改，修改要发布新版本。`0.y.z` 表示初始开发阶段，公开接口不视为稳定。

**来源：** SemVer

## 合并方式

### 项目内统一合并策略 【推荐】

选定 squash、merge 或 rebase 中的一种。推荐 squash，让主分支每个提交对应一个完整改动。
