# 领域建模

本文说明何时使用领域驱动设计（DDD），以及用到时的基本规则。表结构设计见 [表结构设计](../data/schema-design.md)。

## 适用范围

### 先判断是否需要 DDD 【推荐】

DDD 的成本是更多的类型、映射和讨论。只有业务规则确实复杂时才值得。通用语言和限界上下文成本低，多数系统都能受益。聚合、领域事件这类战术模式按下表判断。

| 情况 | 做法 |
|---|---|
| 规则多、状态转换复杂、领域专家能持续参与 | 使用实体、值对象和聚合 |
| 增删改查为主，规则很少 | 普通分层即可，不引入聚合和领域事件 |
| 技术型服务，比如日志收集、文件转码 | 不用 DDD，按数据流组织 |
| 同一系统内复杂度不均 | 只在复杂模块使用，其他模块保持简单 |

**原因：** 对简单模块套用战术模式，只会增加映射代码，不会减少缺陷。

**来源：** Fowler DDD

## 领域语言

### 代码使用业务的词 【推荐】

类型、函数、表和接口的命名，与业务人员的说法一致。同一概念只用一个词，不同概念不共用一个词。发现词不好用时，和业务人员一起改，再同步到代码。

**原因：** 软件无法处理歧义。业务和代码各说一套时，每次沟通都要翻译，翻译错误就会变成缺陷。

**示例：**

| 写法 | 判断 |
|---|---|
| 业务说“退款”，代码叫 `reverseTransaction` | 反例 |
| 业务说“退款”，代码叫 `refund` | 正例 |

**来源：** Fowler 通用语言

### 同一个词在不同上下文可以有不同模型 【推荐】

大型系统无法维持一个统一模型。“客户”在销售和客服中的属性和规则不同时，应拆成两个模型，不做包含所有字段的“大客户对象”。每个上下文的职责、主要术语和对应关系写入 [项目文档](../../general/project-docs.md)。

**原因：** 强行统一的模型会同时受多方需求牵制，谁都改不动。

**来源：** Fowler 限界上下文

## 实体和值对象

表和概念分层一致，见 [表结构设计](../data/schema-design.md)。

### 按是否需要追踪身份来区分 【推荐】

| 类型 | 判断依据 | 相等比较 | 示例 |
|---|---|---|---|
| 实体 | 属性变化后仍是同一个事物 | 按标识 | 订单、账户 |
| 值对象 | 属性完全相同就可以互换 | 按全部属性 | 金额、日期区间 |

同一概念在不同系统可以属于不同类型。比如地址在电商系统通常是值对象，在地图系统可能是实体。

默认先按值对象建模，只有需要追踪身份时才升级为实体。

**来源：** Fowler 值对象、Azure 战术 DDD

### 值对象不可变 【推荐】

修改值对象时创建新对象，不修改原对象。

**原因：** 可变的共享值对象会产生别名问题：改一处，另一处跟着变。

**来源：** Fowler 值对象、Azure 战术 DDD

### 用值对象承载校验和单位 【推荐】

金额、邮箱这类有格式或单位的值，用值对象表达，创建时校验。不要用裸数字和字符串到处传递。

### 业务规则放在拥有数据的对象上 【推荐】

使用领域模型时，状态转换和校验放在实体内。实体只有字段和读写方法、规则全在服务里，属于贫血模型：既付出了映射成本，又得不到模型的好处。

应用服务保持轻量，只负责协调和委托。

不使用领域模型的简单模块不受此约束，事务脚本式的服务是合理选择。

**来源：** Fowler 贫血模型、Azure 战术 DDD

## 聚合

### 聚合是一致性边界 【推荐】

聚合把必须同时满足不变量的对象放在一起，其中一个实体作为根。修改通过根进行，由根保证不变量。

**原因：** 绕过根修改内部对象，不变量就没有人负责。

**示例：** 订单和订单行是一个聚合。“订单总额等于各行之和”由订单这个根保证，不允许外部直接改订单行。

**来源：** Fowler 聚合、Azure 战术 DDD

### 外部只引用聚合根 【推荐】

外部代码不持有聚合内部对象的引用。一个聚合引用另一个聚合时，只保存对方的标识。

**示例：**

反例：

```json
{ "orderId": "1001", "customer": { "id": "7", "name": "张三", "level": 3 } }
```

正例：

```json
{ "orderId": "1001", "customerId": "7" }
```

**来源：** Fowler 聚合、Azure 战术 DDD

### 一个事务只改一个聚合 【推荐】

聚合是加载、保存和事务的单位。跨聚合的变化通过领域事件或应用层的后续步骤完成，并接受最终一致。

**例外：** 单体内多个聚合必须同时成功、业务不接受中间状态时，可以放在同一事务。这时先检查聚合边界是否划错。

**来源：** Fowler 聚合

### 聚合保持小 【推荐】

只放必须在同一事务内一致的数据。生命周期不同的对象分成不同聚合，否则互不相关的更新会争用同一把锁。

**来源：** Azure 战术 DDD

## 领域事件

### 事件表达有业务意义的已发生事实 【推荐】

事件用过去时命名，描述业务上发生了什么，不描述数据库发生了什么。

**示例：**

| 名称 | 判断 |
|---|---|
| `OrderRowUpdated` | 反例：这是技术操作 |
| `DeliveryCanceled` | 正例：这是业务事实 |

**来源：** Azure 战术 DDD

### 事件内容不可修改 【推荐】

事件产生后不再改动。原事件有误时，发出新的更正事件。需要区分时，分别记录事件发生时间和系统得知时间。

**来源：** Fowler 领域事件

### 期望对方执行时用命令 【推荐】

发送方需要接收方完成某件事时，就发命令，不要伪装成事件。事件的发送方不关心谁响应。

**来源：** Fowler 事件驱动

### 注意事件隐藏的流程 【推荐】

用事件串联多步业务时，代码中看不到完整流程，只能靠运行时观察。步骤多、需要整体把控时，改用显式编排，见 [一致性](../reliability/consistency.md) 的 Saga 部分。

**来源：** Fowler 事件驱动

### 消费者只能看到已提交的事件 【必须】

跨模块或跨服务的事件只有在事务提交后才能被消费者看到。保证方式见 [一致性](../reliability/consistency.md) 的 Outbox 部分，投递和消费规则见 [消息](../async/messaging.md)。

**来源：** Azure 战术 DDD

### 不默认使用事件溯源和 CQRS 【推荐】

事件溯源和 CQRS 是两个独立的模式，都会明显增加复杂度。只有审计、历史重建或读写模型差异确实需要时才引入。

**来源：** Fowler 事件驱动
