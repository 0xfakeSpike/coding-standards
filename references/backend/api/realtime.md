# 实时通信

本文讲服务端向客户端推送的方案。认证模型见 [authentication.md](../security/authentication.md)，跨站风险见 [web-risks.md](../security/web-risks.md)，背压的通用策略见 [resilience.md](../reliability/resilience.md)。

## 选型

### 选择满足需求的最简单方案 【推荐】

| 方案 | 适用场景 | 注意 |
|---|---|---|
| 轮询 | 更新不频繁，几秒的延迟可以接受 | 最简单，不占长连接 |
| SSE | 只需服务端推送，如通知、进度、流式输出 | 基于 HTTP，内置重连，只传 UTF-8 文本 |
| WebSocket | 双向高频通信，如协作、聊天 | 鉴权、心跳、重连都要自己实现 |

客户端只是偶尔发消息时，用 SSE 接收，用普通 HTTP 请求发送。

### SSE 使用 HTTP/2 【推荐】

HTTP/1.1 下，浏览器对每个域名只允许约 6 条连接，且跨标签页共享，打开多个标签页就会耗尽。

**来源：** MDN

### 配置链路上的代理 【推荐】

反向代理和负载均衡要支持 WebSocket 升级，长连接的读超时要大于心跳间隔。SSE 响应使用 `text/event-stream` 和 `Cache-Control: no-cache`，并关闭代理缓冲。

**示例：**

```http
HTTP/1.1 200 OK
Content-Type: text/event-stream
Cache-Control: no-cache
X-Accel-Buffering: no
```

**原因：** 代理缓冲会让事件积压，代理超时会周期性切断空闲连接。

**来源：** MDN、OWASP WebSocket 速查表

## 鉴权

### 生产环境使用 wss 和 https 【必须】

**适用：** 线上服务

不使用未加密的 `ws://`。

**来源：** OWASP WebSocket 速查表

### 握手时校验 Origin 【必须】

用明确的白名单比较完整的 Origin，不用通配符或子串匹配，不通过时返回 403。使用 Cookie 认证时，配合 `SameSite` 和 CSRF 令牌。

**原因：** 浏览器握手时自动携带 Cookie，恶意网站可以借用户身份建立连接。

**边界：** Origin 只防浏览器场景，非浏览器客户端可以伪造，不能代替身份认证。

**来源：** OWASP WebSocket 速查表、MDN

### 令牌不放在 URL 【必须】

URL 会进入访问日志。WebSocket 优先在建立连接后用首条消息发送令牌，认证完成前只接受认证消息，不发送受保护的数据，失败或超时就关闭。消息日志同样不记录令牌。

原生 `EventSource` 只能通过 `withCredentials` 携带 Cookie。需要 `Authorization` 头时，改用基于 fetch 的客户端。

**示例：**

反例：

```text
wss://api.example.com/socket?token=eyJhbGciOi
```

正例：

```json
{ "type": "auth", "token": "eyJhbGciOi" }
```

**来源：** OWASP WebSocket 速查表

### 连接的权限随会话变化 【必须】

**适用：** 高风险

会话过期或用户登出时关闭对应连接，长连接定期重新校验。为此要维护会话到连接的映射。

**来源：** OWASP WebSocket 速查表

### 每条消息单独授权和校验 【必须】

建立连接不代表可以执行所有操作。每个动作和订阅都检查权限，消息按不可信输入校验结构，并限制大小和频率。

**来源：** OWASP WebSocket 速查表

### 限制连接数 【必须】

**适用：** 线上服务

按用户和 IP 限制并发连接，未认证的连接限制更严，并设认证超时。

**来源：** OWASP WebSocket 速查表

## 心跳

### 长连接必须有心跳 【必须】

**适用：** 线上服务

服务端定期发送心跳，连续超时未响应就关闭并释放资源。间隔要小于链路上最短的空闲超时。

| 协议 | 方式 |
|---|---|
| WebSocket，服务端探测 | Ping 帧，对端回 Pong |
| WebSocket，浏览器探测 | 应用层心跳消息，因为浏览器 API 不能发送 Ping |
| SSE | 定期发送以冒号开头的注释行 |

**示例：**

```text
: ping

event: order.updated
id: 1042
data: {"orderId":"1001","status":"paid"}

```

**原因：** 网络中断时对端可能收不到任何通知，半开连接会一直占用资源。

**来源：** MDN

## 重连

### 客户端重连使用退避和抖动 【必须】

**适用：** 线上服务

使用指数退避加随机抖动，并设上限。鉴权失败等不可恢复的关闭不要重连。SSE 可以用 `retry` 字段设置重连等待时间。

**原因：** 服务重启时，所有客户端同时重连会形成流量尖峰。

### 重连后能补齐遗漏的消息 【推荐】

SSE 事件带 `id`，断线重连时浏览器通过 `Last-Event-ID` 请求头告知最后收到的事件。WebSocket 由客户端在重连后发送最后的序号。服务端保留一段时间的消息，超出保留范围时通知客户端重新拉取全量数据。

**例外：** 实时行情这类只关心最新值的数据，可以不补发。

### 推送不作为数据的唯一来源 【推荐】

推送用于及时通知，完整状态可以通过 HTTP 接口读取。重连后以接口结果为准。

### 下线时通知客户端 【推荐】

服务停机前发送关闭帧，并让客户端分批重连到其他实例。优雅停机见 [operations.md](../reliability/operations.md)。

## 消息顺序

### 消息带序号 【推荐】

单条连接内消息有序，但重连和多实例之后没有全局顺序。按业务实体或频道分配递增序号，客户端据此发现缺口和乱序，不依赖到达顺序或客户端时间。

**示例：**

```json
{ "type": "order.updated", "channel": "order:1001", "seq": 42, "data": { "status": "paid" } }
```

### 消息处理保持幂等 【推荐】

补发会产生重复，客户端按消息 ID 或序号去重。需要送达确认时，由应用层协议实现。

### 消息使用统一的信封 【推荐】

定义 `type`、`id` 和 `data` 等字段，错误也用同一结构。类型和字段写进契约。

### 服务端控制发送缓冲 【必须】

**适用：** 线上服务

浏览器的 `WebSocket` 接口不支持背压，消息过快时会占满内存。服务端为每条连接设置发送队列上限，慢客户端按策略丢弃、合并或断开。

**来源：** MDN

### 多实例广播走消息中间件 【推荐】

连接分散在多个实例上，实例之间通过发布订阅转发。投递语义见 [messaging.md](../async/messaging.md)。
