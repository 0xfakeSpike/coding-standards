# 缓存和 Redis

本文讲服务端缓存。分布式锁见 [consistency.md](../reliability/consistency.md)，性能优化的通用方法见 [performance.md](../reliability/performance.md)。

## 是否使用缓存

### 先确认缓存有收益 【推荐】

缓存适合读多写少、能容忍短暂旧数据的场景。多数请求都不命中时，检查和写入缓存的开销可能超过收益。

**来源：** Azure Cache-Aside 模式

### 缓存不是数据的主存储 【必须】

事实数据以数据库为准。缓存随时可能过期或被淘汰，业务判断不依赖缓存中的值。

**来源：** Azure 缓存指南

### 敏感数据谨慎缓存 【必须】

权限判断和安全相关的数据直接读主存储。确需缓存时，按用户隔离 Key，并控制谁能访问缓存实例。

**来源：** Azure Cache-Aside 模式

### 可选缓存故障时回源 【推荐】

项目要明确缓存是否为必需依赖。可选缓存不可用时回源，等待缓存要有超时。高流量系统评估回源对数据库的压力，手段见 [resilience.md](../reliability/resilience.md)。

**来源：** Azure 缓存指南

## 缓存模式

### 默认使用 Cache-Aside 【推荐】

读取时先查缓存，未命中再读数据库并写入缓存。写入时先更新数据库，再删除缓存。

**原因：** 删除比更新缓存更安全。两个并发写入更新缓存时，后写入缓存的可能是旧值。

**示例：**

反例：先删除缓存，再更新数据库。在这个间隙读取的请求会把旧值写回缓存。

正例：

```text
读：GET order:1001，未命中时查询数据库，SET order:1001 并设置 TTL
写：UPDATE orders，提交后 UNLINK order:1001
```

**来源：** Azure Cache-Aside 模式

### 写后立即读新值的路径不走旧缓存 【推荐】

Cache-Aside 不保证缓存和数据库一致，写入后到下一次读取之间可能短暂读到旧值。需要写后立即读到新值的路径，直接读数据库或使用写穿透。

**来源：** Azure Cache-Aside 模式

### 用 TTL 兜底一致性 【必须】

缓存都设置 TTL。TTL 决定了删除失败或并发竞争时旧数据最长存在多久，要按业务能接受的时长设置。TTL 过短会频繁回源，过长会放大旧数据的影响。

**例外：** 全量常驻内存的静态数据可以启动时预热，不设过期时间。

**来源：** Azure Cache-Aside 模式

### 本地缓存使用更短的 TTL 【推荐】

进程内缓存在各实例上各有一份，彼此很快就会不一致。只放变化很少的数据，或者用较短的 TTL。

**来源：** Azure Cache-Aside 模式

## 穿透、击穿和雪崩

### 防范三类回源风险 【推荐】

| 问题 | 原因 | 对策 |
|---|---|---|
| 穿透 | 查询不存在的数据，每次都回源 | 缓存空值并用较短的 TTL，或用布隆过滤器 |
| 击穿 | 热点 Key 过期，大量请求同时回源 | 互斥回源，或者在过期前提前刷新 |
| 雪崩 | 大量 Key 同时过期，或缓存整体不可用 | TTL 加随机抖动，回源限流 |

**示例：**

反例：批量预热时全部使用相同的 TTL。

```text
SET product:1001 ... EX 3600
SET product:1002 ... EX 3600
```

正例：TTL 在基准值上加随机抖动。

```text
SET product:1001 ... EX 3487
SET product:1002 ... EX 3712
```

## Key 规范

### Key 使用统一的分段格式 【必须】

Redis 没有命名空间，靠 Key 的结构避免冲突。用冒号分段，第一段是业务前缀，格式为 `对象类型:ID`。

**示例：**

反例：

```text
u1000flw
1001
```

正例：

```text
user:1000:followers
order:1001
```

**来源：** Redis 文档

### Key 不要过长 【推荐】

过长的 Key 占用内存，查找时比较也更慢。需要用长内容做 Key 时，先取哈希值。

**来源：** Redis 文档

### 业务代码不用 KEYS 【必须】

**适用：** 线上服务

`KEYS` 在大数据集上严重影响性能，只用于调试。遍历用 `SCAN`，或者用集合维护需要枚举的 Key。

**来源：** Redis 文档

### 集群的多 Key 操作使用哈希标签 【推荐】

Redis Cluster 中，多 Key 操作要求所有 Key 在同一个槽。用 `{...}` 标记参与哈希的部分，比如 `{user:1000}:following` 和 `{user:1000}:followers`。标签的取值要足够分散，否则数据会集中到少数节点。

**来源：** Redis 文档

## 大 Key 和热 Key

### 避免大 Key 【推荐】

单个 Key 的值或元素数量要有上限，阈值由项目确定。集合类数据按 ID 或时间拆成多个 Key，只读取需要的部分。

**原因：** Redis 按单线程执行命令，操作大 Key 会阻塞其他请求，并造成网络和内存尖峰。

**工具：** 用 `redis-cli --bigkeys`、`--memkeys` 或 `--keystats` 查找。

**来源：** Redis 文档

### 删除大 Key 用 UNLINK 【推荐】

`UNLINK` 在后台线程回收内存，不阻塞。`DEL` 可能同步回收并阻塞其他命令。

**来源：** Redis 文档

### 分散热 Key 【推荐】

单个 Key 的访问量超过单节点能力时，用进程内缓存加短 TTL，或者把值复制到多个带后缀的 Key，读取时随机选择。

**工具：** `redis-cli --hotkeys` 查找热 Key，要求 `maxmemory-policy` 是 LFU 类策略。

**来源：** Redis 文档

## 内存和淘汰

### 设置内存上限和淘汰策略 【必须】

**适用：** 线上服务

缓存实例要设置 `maxmemory` 和淘汰策略。64 位系统默认不限制内存。有副本或持久化时要预留缓冲区内存，它不计入 `maxmemory`。

| 场景 | 策略 |
|---|---|
| 纯缓存，部分数据访问更频繁 | `allkeys-lru`，这是不确定时的合理默认 |
| 各 Key 访问频率相近 | `allkeys-random` |
| 不允许丢数据 | `noeviction`，写满后写命令报错 |

`volatile-*` 策略在没有设置过期时间的 Key 上不生效，效果等同 `noeviction`。

**来源：** Redis 文档

### 缓存和持久数据分开实例 【推荐】

缓存可以被淘汰，持久数据不能，两者的淘汰策略互相冲突。

**来源：** Redis 文档

### 监控命中率 【推荐】

用 `INFO stats` 的 `keyspace_hits` 和 `keyspace_misses` 计算命中率，并据此调整 TTL 和淘汰策略。指标告警见 [metrics-and-alerts.md](../observability/metrics-and-alerts.md)。

**来源：** Redis 文档
