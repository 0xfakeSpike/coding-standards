# 文档数据库和搜索

本文讲 MongoDB 和 Elasticsearch。关系型数据库见 [schema-design.md](schema-design.md)。

## 选型边界

### 默认使用关系型数据库 【推荐】

先用关系型数据库。下列需求明确时再引入其他存储，每多一种存储，就多一套运维、备份和同步。

| 需求 | 选择 |
|---|---|
| 事务、关联查询、结构稳定的数据 | MySQL、PostgreSQL |
| 结构差异大、整体读写、按聚合访问的数据 | MongoDB |
| 全文检索、相关性排序、多维筛选和聚合 | Elasticsearch |

### Elasticsearch 不作为事实来源 【必须】

Elasticsearch 中的数据是从主存储派生的索引，主存储丢失时无法靠它恢复业务数据。业务判断读主存储，不读搜索结果。

**原因：** 同步有延迟，写入后最多约 1 秒才能被搜索到，同步失败时差距更大。

**来源：** Elasticsearch 文档

## MongoDB 建模

### 按访问模式设计文档 【推荐】

先列出最频繁的读写操作，再决定文档结构。一起访问的数据放在一起，不照搬关系型的表结构。

**来源：** MongoDB 文档

### 默认嵌入，频繁更新时引用 【推荐】

| 情况 | 选择 |
|---|---|
| 包含关系，子数据总和父数据一起读 | 嵌入 |
| 一对多，子数据数量有上限 | 嵌入 |
| 关联数据频繁更新，或被多处共享 | 引用 |
| 子数据数量没有上限 | 引用 |

嵌入能用一次操作读取，并在一次原子写入中更新。引用只需更新一处，但读取要多一次查询或 `$lookup`。

**来源：** MongoDB 文档

### 不使用无上限的数组 【必须】

数组元素会一直增长时，放到单独的集合，或者只嵌入最常用的少量元素。

**原因：** 单个文档必须小于 16 MiB。无上限的数组还会拖慢索引和应用。

**示例：**

反例：

```json
{ "title": "商品 A", "reviews": [ { "user": "u1", "text": "..." } ] }
```

正例：

```json
{ "title": "商品 A", "recent_reviews": [ { "user": "u1", "text": "..." } ] }
```

```json
{ "product_id": "p1", "user": "u1", "text": "..." }
```

第二个文档放在 `reviews` 集合中，商品文档只保留最近几条。

**来源：** MongoDB 文档

### 重复数据要有同步方案 【推荐】

很少变化的数据才适合重复存储。重复之前确定是否需要立即一致，以及用事务还是异步同步。

**来源：** MongoDB 文档

### 结构稳定后启用校验 【推荐】

MongoDB 默认不约束文档结构。应用的结构确定后，用 `$jsonSchema` 校验必填字段、类型和取值范围，防止写入错误数据。

**来源：** MongoDB 文档

### 优先靠文档结构保证原子性 【推荐】

单文档操作是原子的。相关数据放进一个文档，可以减少对多文档事务的需要。必须使用多文档事务时保持简短，默认运行时长不能超过一分钟，超时会被中止。

**来源：** MongoDB 文档

### 复合索引遵循 ESR 【推荐】

等值字段放最前面。要避免内存排序时，排序字段放在范围字段之前。范围条件选择性很高时，把范围字段放在排序字段之前。

**来源：** MongoDB 文档

## Elasticsearch 映射

### 生产索引使用显式映射 【必须】

**适用：** 线上服务

已知字段在创建索引时明确定义类型，不依赖动态映射的推断。用 `dynamic` 控制未知字段：`strict` 拒绝文档，`false` 不索引新字段。

**原因：** 自动推断的类型可能不合需要，而已有字段的映射通常不能修改。

**示例：**

```json
{
  "mappings": {
    "dynamic": "strict",
    "properties": {
      "sku": { "type": "keyword" },
      "title": { "type": "text" },
      "price": { "type": "scaled_float", "scaling_factor": 100 },
      "created_at": { "type": "date" }
    }
  }
}
```

**来源：** Elasticsearch 文档

### 区分 text 和 keyword 【推荐】

| 类型 | 用途 |
|---|---|
| `text` | 分词后全文检索，如标题、正文 |
| `keyword` | 精确匹配、排序、聚合，如状态、标签、邮箱 |

数字形式的标识符不做范围查询时用 `keyword`，`term` 查询通常更快。同时需要两种用法时，用多字段映射。

**来源：** Elasticsearch 文档

### 防止映射膨胀 【必须】

**适用：** 线上服务

不把用户输入或动态值用作字段名。键很多且不固定的对象用 `flattened` 类型。保留 `index.mapping.total_fields.limit` 的限制，不靠调大它解决问题。

**原因：** 字段过多会导致内存不足，集群也难以恢复。

**来源：** Elasticsearch 文档

### 索引配置放在模板中 【推荐】

用索引模板定义映射和设置，公共部分抽成组件模板，并纳入版本控制。模板只在创建索引时生效，修改后不影响已有索引。

**来源：** Elasticsearch 文档

### 应用通过别名访问索引 【推荐】

应用只使用别名。需要改映射时，新建索引，用 `_reindex` 导入数据，再用一次别名操作原子切换。

**示例：**

```json
{
  "actions": [
    { "remove": { "index": "products_20261001", "alias": "products" } },
    { "add": { "index": "products_20261105", "alias": "products" } }
  ]
}
```

**来源：** Elasticsearch 文档

## 查询和同步

### 深分页使用 search_after 【必须】

`from` 加 `size` 默认不能超过 10000 条，越深越耗内存。深分页用 `search_after` 配合时间点（PIT），用完删除 PIT，不用 `scroll` 做深分页。

**来源：** Elasticsearch 文档

### 写入后不立即依赖搜索结果 【必须】

写入要等刷新后才能被搜索到。不靠每次写入都强制刷新解决。写后立即展示的页面，读主存储。

**来源：** Elasticsearch 文档

### 异步同步到搜索索引 【推荐】

不在业务请求里同步写两个存储。主存储提交后，通过消息或变更捕获更新索引，投递可靠性见 [consistency.md](../reliability/consistency.md)，消费规则见 [messaging.md](../async/messaging.md)。

同步要满足：

- 用主键作为文档 `_id`，重复写入结果不变。
- 用递增的外部版本号（`version_type=external`）防止乱序的旧数据覆盖新数据。
- 能从主存储全量重建索引，这也是数据不一致时的修复手段。
