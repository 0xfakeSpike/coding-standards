# 表结构设计

以关系型数据库（MySQL、PostgreSQL）为主，具体语法以所用数据库为准。索引见 [indexes-and-queries.md](indexes-and-queries.md)，结构变更见 [migrations.md](migrations.md)。

## 表和字段的取舍

### 表要少 【必须】

同类数据放一张表，用字段区分类型或状态，不为每个类型或状态单独建表。

**原因：** 表越多，查询、迁移和数据访问代码越多，同一规则也容易在多张表上各写一遍。

**示例：**

反例：`system_notices`、`promo_notices`、`archived_notices` 三张结构相同的表。

正例：一张 `notices` 表，用 `type` 区分类型，用 `status` 区分是否归档。

**例外：** 概念不同的数据不合并，见“表要和概念分层一致”。

**来源：** 团队

### 字段要精简 【必须】

每个字段都要问是否必须：谁写入、谁读取、不存会怎样。答不上来就不加。`created_at`、`updated_at` 这类基础字段保留。

**原因：** 多余字段要持续写入、校验和迁移，还会让人误以为它有业务含义。

**来源：** 团队

### 表要和概念分层一致 【必须】

表的划分和层级跟随业务概念的分层。一个概念对应一张表，上下级关系用外键字段表达，不出现对应不到概念的中间表，也不把不同层级的概念压进一张表。

**示例：**

反例：`orders` 表里放 `item1_sku`、`item2_sku`，把订单和订单行压在一层。

正例：`orders` 和 `order_items` 两张表，`order_items.order_id` 指向上级。

概念的划分方法见 [domain-modeling.md](../architecture/domain-modeling.md)。

**来源：** 团队

### 业务逻辑不放数据库 【必须】

业务规则写在应用的业务层，不写进触发器、存储过程、存储函数、视图里的计算逻辑和数据库定时事件。数据库只负责存储和数据完整性。分层见 [layering.md](../architecture/layering.md)。

| 放在数据库 | 不放在数据库 |
|---|---|
| `NOT NULL`、唯一约束、外键、取值范围的 `CHECK` | 状态流转、金额计算、权限判断 |
| 索引、字段默认值 | 用触发器同步其他表、发通知、写业务日志 |
| 迁移工具运行期间自行创建的临时对象 | 用存储过程编排业务流程 |

**原因：** 数据库里的逻辑不随应用代码评审和测试，调用方看不见副作用，排查时也难以追踪。

**例外：** 约束不算业务逻辑，应当使用。业务唯一性必须由唯一索引保证。

**来源：** 团队、Azure 繁忙数据库

### 没有读取方的字段和表要删除 【必须】

确认没有读取方后，字段和表直接删除，不继续写入和保留。判断方法和生产数据的确认要求见 [deletion.md](../../general/deletion.md)。

**来源：** 团队

### 表和字段写注释 【必须】

**适用：** 多人协作

表和字段都写注释，枚举字段列出每个取值的含义。这是存放在数据库里的元数据，不是代码注释，不受“代码中不写注释”的限制。

**示例：**

```sql
CREATE TABLE orders (
  id BIGINT PRIMARY KEY COMMENT '订单 ID',
  status VARCHAR(20) NOT NULL COMMENT '状态：pending 待支付，paid 已支付，closed 已关闭'
) COMMENT = '订单';
```

PostgreSQL 使用单独的语句：

```sql
COMMENT ON COLUMN orders.status IS '状态：pending 待支付，paid 已支付，closed 已关闭';
```

## 命名

### 使用统一的命名规则 【必须】

表名和字段名使用小写 `snake_case`，不使用保留字。表名单复数全库统一。

| 对象 | 规则 | 示例 |
|---|---|---|
| 主键 | `id` | `id` |
| 外键字段 | `<单数表名>_id` | `user_id` |
| 布尔字段 | `is_` 开头 | `is_active` |
| 时间字段 | `_at` 结尾 | `paid_at` |
| 普通索引 | `idx_表_字段` | `idx_orders_user_id` |
| 唯一索引 | `uk_表_字段` | `uk_users_email` |

## 基础字段和类型

### 每张表有主键和时间字段 【必须】

每张表都有主键和 `created_at`、`updated_at`。这是排障和数据同步的基础。

### 金额不用浮点类型 【必须】

金额使用 `DECIMAL` 或以分为单位的 `BIGINT`，不用 `FLOAT`、`DOUBLE`。

**原因：** 浮点数无法精确表示十进制小数，累加后会出现误差。

### 时间统一按 UTC 存储 【必须】

表示某一时刻的字段统一按 UTC 存储。PostgreSQL 使用 `timestamptz`，它内部按 UTC 保存，不保留原始时区。MySQL 的 `TIMESTAMP` 上限是 2038 年，并随连接时区转换，长期使用的字段用 `DATETIME` 并约定写入 UTC。

**例外：** 营业时间这类本地挂钟时间不代表某一时刻，用不带时区的类型。

**来源：** MySQL 手册、PostgreSQL 文档

### MySQL 字符集使用 utf8mb4 【必须】

不使用 `utf8mb3`（旧称 `utf8`）。它每字符最多 3 字节，只支持基本多文种平面，无法存储 Emoji 等补充字符。

**来源：** MySQL 手册

### 字段默认非空 【推荐】

字段默认 `NOT NULL` 并设置合适的默认值。`NULL` 只用于确实表示“未知”的情况，因为它会让比较和聚合更复杂。

### 选择合适的最小类型 【推荐】

按取值范围选类型，不把所有字段都定义成 `VARCHAR(255)`。参与比较和关联的字段，类型和排序规则保持一致。

### JSON 字段不替代建模 【推荐】

需要查询、约束或关联的数据放独立字段。JSON 只存整体读写、结构确实不固定的内容。

## 范式和反范式

### 默认遵守第三范式 【推荐】

一个事实只存一处。反范式必须有实测的读取瓶颈作为依据，并说明冗余字段由谁维护。

**原因：** 冗余数据需要同步，同步漏掉时两份数据互相矛盾。

**示例：** 业务判断以事实数据为准，不依赖冗余的计数或状态，见 [consistency.md](../reliability/consistency.md)。

## 主键和外键

### 主键短且大致递增 【推荐】

主键使用 `BIGINT` 自增、雪花 ID 或 UUIDv7。随机 UUIDv4 作为聚簇主键时写入性能较差。对外暴露时避免可枚举的自增 ID。

**原因：** InnoDB 的二级索引记录都包含主键，主键越长，所有二级索引越大。

**来源：** MySQL 手册

### 外键约束按项目统一决定 【推荐】

小型系统使用外键能保证完整性。高并发或分库分表系统通常放到应用层保证。选择记入项目文档，同一项目不混用。

**示例：** `gh-ost` 不支持带外键的表，打算使用它做大表变更时要提前考虑。

**来源：** gh-ost 文档

## 软删除

### 按需使用软删除 【推荐】

不默认给所有表加软删除。使用 `deleted_at` 时注意：

- 所有查询都要过滤，在数据访问层统一处理，见 [data-access.md](data-access.md)。
- 唯一约束要把软删除考虑进去。
- 合规要求彻底删除的数据不能只做软删除，见 [privacy.md](../security/privacy.md)。

PostgreSQL 用部分唯一索引，只约束未删除的行：

```sql
CREATE UNIQUE INDEX uk_users_email ON users (email) WHERE deleted_at IS NULL;
```

MySQL 的唯一索引允许多个 `NULL`，把可空的 `deleted_at` 加进去约束不住未删除的行。改用非空的删除标记字段，未删除时为 0，删除时写入主键值：

```sql
ALTER TABLE users
  ADD COLUMN deleted_mark BIGINT NOT NULL DEFAULT 0,
  ADD UNIQUE KEY uk_users_email (email, deleted_mark);
```

**来源：** MySQL 手册、PostgreSQL 文档

## 多租户

### 共享库的租户数据带 tenant_id 【必须】

共享数据库时，租户数据表都有 `tenant_id`，并放在唯一索引和常用索引的最左侧。过滤条件由数据访问层统一加上，不靠每个调用方记得。

**原因：** 漏掉一处过滤就是跨租户数据泄露。

### 不按租户建表或加字段 【推荐】

不给每个租户单独建表，也不为单个租户的需求加字段。

**原因：** 租户增多后，表数量和定制字段都无法管理。

**来源：** Azure 多租户存储

### 按隔离要求选择方案 【推荐】

默认共享表。合规要求物理隔离，或者个别租户负载影响其他租户时，再用独立数据库或分片。PostgreSQL 的行级安全可以作为第二道防线，但表所有者默认绕过策略，需要 `FORCE ROW LEVEL SECURITY`，超级用户和 `BYPASSRLS` 角色始终绕过。

**来源：** Azure 多租户存储、PostgreSQL 文档

## 分库分表

### 单库能解决就不分片 【推荐】

先用索引优化、历史数据归档和读副本解决。分片会带来跨片查询、跨片事务和数据再平衡的长期成本。

### 分片键慎重选择 【推荐】

分片键要不可变、基数高、分布均匀，并匹配主要查询，使多数请求落在单个分片。避免自增值、连续时间、低基数字段和频繁变化的字段。

**原因：** 分片键上线后再改，通常要迁移全部数据。选错还会形成热点分片。

**示例：** 用多个逻辑分片映射到较少的物理节点，再平衡时只需调整映射。

**来源：** Azure 分片模式
