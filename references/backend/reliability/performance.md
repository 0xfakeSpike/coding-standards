# 后端性能

本文讲后端特有的性能手段。先测量、前后对比和报告数字的要求见 [性能方法](../../general/performance.md)。SQL 和索引优化见 [索引与查询](../data/indexes-and-queries.md)，缓存见 [缓存与 Redis](../data/cache-and-redis.md)。

## 性能剖析

### 先定位到组件，再定位到代码 【推荐】

先用现有的追踪、指标或日志找到慢在哪个服务或依赖，再对该进程做剖析。不凭感觉改代码。

### 区分 CPU 时间和等待时间 【推荐】

| 现象 | 分析方式 |
|---|---|
| CPU 高 | 采样剖析，用火焰图看最宽的调用栈 |
| CPU 不高但请求慢 | 分析等待时间，比如 I/O、锁和连接池 |

**原因：** CPU 剖析只能看到线程在运行时的情况。后端的慢请求多数是在等待，只看 CPU 火焰图找不到原因。

**来源：** Gregg 火焰图、Gregg Off-CPU 分析

## 连接池

### 复用连接 【必须】

数据库、缓存和 HTTP 客户端都使用连接池，不在每次请求时新建连接。客户端对象全局创建一次。

### 连接池不是越大越好 【推荐】

连接池大小根据压测确定。起点可以用数据库 CPU 核数的两倍左右，再按实测调整。

**原因：** 连接数超过数据库的处理能力后，上下文切换和锁竞争会让所有请求变慢。缩小连接池常常能同时降低延迟。

**示例：**

```json
{ "pool": { "maxSize": 20, "acquireTimeoutMs": 500 } }
```

**来源：** HikariCP 文档

### 所有实例的总连接数不超过上限 【必须】

**适用：** 线上服务

单实例连接池大小乘以最大实例数，要小于数据库的连接上限，并给运维工具留出余量。扩容前要先算这个数字。

### 获取连接要有超时 【必须】

**适用：** 线上服务

等不到连接时快速失败，不无限排队。获取连接的超时计入请求的时间预算，见 [弹性设计](resilience.md)。监控使用中的连接数、等待数和等待时长。

### 持有连接的时间要短 【必须】

**适用：** 线上服务

持有连接期间不调用外部服务，也不做耗时计算。一个请求同时占用多个连接时，容易造成连接池死锁，要先从代码上消除。

**来源：** HikariCP 文档

## 批处理

批量接口的部分失败语义见 [rest.md](../api/rest.md)，逐条处理时要能只重试失败的条目。

### 消除循环中的远程调用 【必须】

**适用：** 线上服务

把循环里的查询和调用改成批量操作。ORM 的隐式加载也会造成 N+1。

**示例：**

反例：

```sql
SELECT id, sku_id FROM order_items WHERE order_id = 1;
SELECT id, sku_id FROM order_items WHERE order_id = 2;
SELECT id, sku_id FROM order_items WHERE order_id = 3;
```

正例：

```sql
SELECT id, sku_id FROM order_items WHERE order_id IN (1, 2, 3);
```

**来源：** Azure 频繁 I/O

### 批量大小有上限 【必须】

**适用：** 线上服务

批量请求要限制条数和字节数，大数据集分批处理，并把发送速率控制在下游可承受范围内。只读取实际需要的字段和行。

**原因：** 过大的批次会造成长事务、内存峰值和超时。

**来源：** Azure 频繁 I/O、Azure 限速

## 压测

**适用：** 线上服务（本节全部规则）

### 压过崩溃点 【推荐】

压到系统出问题，再继续加压。过载时吞吐应该保持平稳，不应该跌到零。没压过崩溃点的服务，要假定它会以最差的方式失败。

**来源：** AWS 负载削减、Google SRE 级联故障

### 用恒定速率发压 【推荐】

测量延迟时用固定到达速率的工具。闭环工具在服务变慢时会自动减速，少算最慢的那部分请求，这称为协同遗漏，会让 P99 看起来好得多。

**工具：** wrk2 的 `-R` 参数可设定恒定吞吐。

**来源：** wrk2 文档

### 环境和数据接近生产 【推荐】

数据量、数据分布和依赖要接近生产。小表上的查询计划和生产不同，请求参数单一时缓存命中率会虚高。同时测量客户端视角的延迟和成功率。

**来源：** AWS 负载削减

## 内存

### 大数据流式处理 【必须】

**适用：** 线上服务

文件、导出和大结果集使用流式读写或分页，不一次性载入内存。

### 内存中的集合和单个请求都有上限 【必须】

**适用：** 线上服务

进程内缓存、队列和累积列表都要有容量上限和淘汰策略。请求体大小、分页大小和批量条数也要限制，否则一个请求就可能耗尽内存。

### 内存上限留余量 【推荐】

容器内存限制要高于稳定峰值，并给运行时的非堆内存留余量。超限时进程会被直接杀掉，见 [容器](../../general/containers.md)。泄漏往往在短测试中看不出来，要用长稳测试观察内存曲线。各语言的运行时调优见语言层。

**来源：** k6 测试类型

## P99 治理

跨实例汇总分位数用直方图，见 [指标和告警](../observability/metrics-and-alerts.md)。

### 分别统计成功和失败的延迟 【推荐】

快速失败的请求会拉低延迟统计。被限流拒绝的请求不混入正常请求的延迟。

**来源：** AWS 负载削减

### 注意高利用率下的延迟 【推荐】

利用率升高时，排队、锁竞争和垃圾回收都会加剧，延迟先于吞吐恶化。P99 目标要在目标利用率下验证，不是在空闲时验证。

**来源：** AWS 负载削减

### 关注扇出放大 【推荐】

一个请求并行调用多个下游时，总延迟取决于最慢的一个。调用 100 个下游时，即使每个只有 1% 的慢请求，也有约 63% 的总请求会被拖慢。减少扇出数量，并给每个下游设定时限。

### 拆解慢请求的时间 【推荐】

用链路追踪分别看排队、处理和下游等待的时间。延迟呈双峰分布时，通常是部分请求卡到超时，这时看平均值没有意义，要看分布。

**来源：** Google SRE 级联故障

### 从根因治理尾延迟 【推荐】

先找到慢的原因，比如锁竞争、垃圾回收和慢查询。不靠调大超时或增加重试掩盖。
