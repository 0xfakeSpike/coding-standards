# 运维就绪

本文规定服务上线前必须具备的运行能力。Kubernetes 探针和资源配置的基础规则见 [容器](../../general/containers.md)，发布见 [发布与回滚](../../general/release.md)。

**适用：** 线上服务（本文全部规则）

## 健康检查

存活和就绪探针的用途、不依赖外部服务和共享依赖的要求见 [容器](../../general/containers.md)。

### 健康检查要轻量 【推荐】

健康检查不执行昂贵操作，过载时也要及时响应。响应慢的健康检查会让实例被误摘除，把压力转移给其他实例。检查接口不暴露内部细节。

**来源：** AWS 健康检查

## 优雅启停

### 准备好之后才接流量 【必须】

建连、加载配置和预热完成后，就绪检查才返回成功。必需依赖的初始化失败时立即退出。启动时间尽量控制在几秒内，启动慢时使用启动探针，不要靠放宽存活探针。

**原因：** 冷启动的实例性能差，缓存为空的实例可能被刚进入的流量打垮。

**来源：** AWS 超时与重试、Google SRE 级联故障、Twelve-Factor App、Kubernetes 探针

### 收到 SIGTERM 后优雅退出 【必须】

| 顺序 | 动作 |
|---|---|
| 1 | 就绪检查转为失败 |
| 2 | 短暂等待负载均衡摘除实例 |
| 3 | 停止接收新请求，完成进行中的请求 |
| 4 | 后台任务归还队列或释放锁 |
| 5 | 关闭连接池，刷出日志和指标后退出 |

**原因：** Kubernetes 中端点摘除和发送 SIGTERM 同时发生，互不等待，收到信号后仍可能有新请求进入。

**来源：** Kubernetes Pod 生命周期、Twelve-Factor App

### 退出时间在宽限期内 【必须】

`terminationGracePeriodSeconds` 默认 30 秒，包含 `preStop` 的时间。超过后进程被 SIGKILL 强杀。应用的退出超时要短于宽限期，宽限期要大于最长请求的处理时间。

信号发给容器的 1 号进程。用 shell 包装启动命令时，要确认信号能传到应用。

**示例：**

```yaml
terminationGracePeriodSeconds: 45
containers:
  - name: api
    lifecycle:
      preStop:
        exec:
          command: ["sleep", "5"]
```

**来源：** Kubernetes Pod 生命周期

### 能承受突然死亡 【必须】

优雅退出不是保证。进程随时可能被杀，长任务要可重入或幂等，由队列或租约机制交给其他实例继续。

**来源：** Twelve-Factor App

## 无状态

进程内定时器在每个实例上都会运行，定时任务的规则见 [后台任务](../async/background-jobs.md)。

### 服务保持无状态 【推荐】

会话、上传文件和任务状态放到外部存储，这样才能水平扩容和随时替换实例。内存和本地磁盘只用于单次请求内的临时数据。会话放到带过期时间的外部存储，不靠粘性会话把用户固定到某个实例。

**来源：** Twelve-Factor App

## SLO

### 从用户视角定义 SLI 【推荐】

SLI 衡量用户实际感受到的质量，不选“容易测”的内部指标。指标数量要少，只留能影响决策的。

| 服务类型 | 常用 SLI |
|---|---|
| 请求响应型 | 成功率、延迟分位数 |
| 数据管道 | 数据新鲜度、处理正确率 |
| 存储 | 可用性、持久性 |

**示例：** 30 天内，成功响应比例不低于 99.9%，并且 99% 的请求在 300 毫秒内完成。

**来源：** Google SRE 服务等级目标

### 目标不设为 100% 【推荐】

目标根据用户需要和成本确定，不是根据当前表现。先从宽松的目标开始，再根据经验收紧。SLO 要接入告警，见 [指标和告警](../observability/metrics-and-alerts.md)。

**原因：** 绝对目标无法实现，也会阻止所有变更。

**来源：** Google SRE 服务等级目标

## 容量规划

### 用压测确定单实例容量 【推荐】

用压测把资源数量换算成服务能力，并定期重做。成本差异大的接口按实际资源消耗计算，不用请求数估算。规划时覆盖数据库连接数、下游配额和队列吞吐，不只看应用实例。方法见 [性能](performance.md)。

**来源：** Google SRE 引言、Google SRE 过载处理、Azure 容量规划

### 容量留出故障余量 【推荐】

容量要能承受一个可用区或部分实例失效。自动扩缩容有延迟，不能只靠它应对突发流量。

**来源：** AWS 负载削减、Azure 节流
