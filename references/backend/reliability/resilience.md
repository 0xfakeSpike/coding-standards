# 弹性设计

本文规定依赖变慢、失败或过载时服务如何自保。语言无关的错误原则见 [错误处理原则](../../general/error-handling.md)。

## 取舍

### 不为罕见失败增加补偿机制 【必须】

不为边角问题增加复杂度。罕见且后果可接受的失败，收益抵不上长期维护成本时，不加回退链路和定时补偿。涉及资金和数据丢失时单独评估，并向用户说明取舍。

**来源：** 团队

## 超时预算

### 所有网络调用设置超时 【必须】

连接超时和请求超时都要设置，包括数据库、缓存和同机的跨进程调用。不使用客户端库的无限等待默认值。

**原因：** 没有超时的调用会一直占用线程、连接和内存，最终拖垮服务。

**来源：** AWS 超时与重试

### 根据下游延迟选择超时 【推荐】

先确定可接受的误超时比例，再取下游对应的延迟分位数。比如接受 0.1% 误超时，就参考 P99.9。跨公网调用要加上最差网络延迟，P99.9 和 P50 很接近时要留余量。还要确认超时是否包含 DNS 解析、TLS 握手和建连。

**原因：** 超时过长起不到保护作用；过短会让大量请求重试，小幅变慢也能演变成故障。

**来源：** AWS 超时与重试

### 整条调用链共享一个时间预算 【推荐】

跨服务调用时，入口确定总时限，向下游传递剩余时间，每一跳的超时不超过剩余时间。服务端有请求排队时，取出后先检查剩余时间，已过期的直接丢弃。单进程服务只要求每次调用有超时。

**原因：** 各层独立设置超时时，上游已经放弃，下游还在继续工作，资源全部浪费。

**示例：**

| 调用 | 反例 | 正例 |
|---|---|---|
| 入口 | 2 秒 | 2 秒 |
| 服务 A 调用服务 B | 5 秒 | 剩余时间减去 A 的后续处理时间 |
| 服务 B 调用数据库 | 10 秒 | 收到的剩余时间减去 B 的后续处理时间 |

**例外：** 机器间时钟不一致时，传递时长比传递绝对时间更可靠。时长要扣除排队和传输时间。

**来源：** Google SRE 级联故障、AWS 负载削减

## 重试和退避

### 重试只用于暂时性失败和可安全重复的操作 【必须】

两个条件都要满足：失败是暂时的，操作重复执行没有副作用或已经幂等。不满足时不重试。

超时不代表对方没有执行。有副作用的操作要先做成幂等，见 [一致性](consistency.md)。

下表的“可以”都以操作幂等为前提，只有明确确认请求未到达服务端的连接失败不要求幂等。

| 失败 | 是否重试 |
|---|---|
| 连接失败、网络中断 | 可以 |
| 503、429 | 可以，遵守 `Retry-After` |
| 502、504 | 可以 |
| 超时 | 可以 |
| 500 | 默认不重试，能确认是暂时故障时可以 |
| 其他 4xx | 不重试 |
| 业务拒绝、程序缺陷 | 不重试 |

**原因：** 重试永久性错误只会增加负载；重试非幂等操作会产生重复扣款这类副作用。

**来源：** AWS 超时与重试、Azure 重试风暴

### 使用带上限的指数退避和抖动 【必须】

重试次数有上限，等待时间指数增长并有封顶，再加上随机抖动。总重试时长不超过调用方的时间预算。定时任务和周期请求同样要错开触发时间。

**原因：** 不退避会加重下游压力；不加抖动时，所有客户端会同时重试，形成新的峰值。

**示例：**

```json
{
  "retry": {
    "maxAttempts": 3,
    "baseDelayMs": 100,
    "maxDelayMs": 2000,
    "jitter": "full"
  }
}
```

**来源：** AWS 超时与重试、Azure 重试风暴

### 只在一层重试 【必须】

**适用：** 线上服务

调用链上只选一层负责重试，通常是离失败最近且能判断错误类型的一层。队列重投、SDK 内置重试也各算一层。

**原因：** 重试次数逐层相乘。五层调用每层试三次，最底层的负载可达 243 倍。

**来源：** AWS 超时与重试、Google SRE 级联故障

### 用重试预算限制总量 【推荐】

高流量客户端除了单次请求的上限，还要限制重试占总请求的比例，或者用令牌桶限制重试速率。依赖不健康时，重试应该自动减少。

**来源：** AWS 超时与重试、Google SRE 过载处理

## 熔断

### 关键依赖按需配置熔断 【推荐】

熔断用于持续故障，不用于瞬时错误。优先使用框架或服务网格的实现。

| 状态 | 行为 | 转换条件 |
|---|---|---|
| 关闭 | 请求放行，统计近期失败 | 时间窗内失败达到阈值，转为打开 |
| 打开 | 请求立即失败 | 等待时间到，转为半开 |
| 半开 | 放行少量试探请求 | 连续成功转为关闭，失败转回打开 |

**例外：** 访问进程内资源、平台已负责故障恢复、消息驱动且有死信队列时，不需要熔断。简单的重试预算足够时不要加熔断，它带来的模式切换难以测试，也可能拉长恢复时间。

**来源：** Azure 断路器、AWS 超时与重试

### 熔断要和其他机制配合 【推荐】

- 重试逻辑识别熔断返回的错误，并停止重试。
- 下游超时要合理。超时过长时，熔断打开前线程已被占满。
- 调用方要处理熔断错误，比如降级或明确报错。
- 状态变化要暴露指标，并能人工强制打开或关闭。
- 下游有多个独立分片时分别熔断，否则一个分片故障会阻断其他分片。

**来源：** Azure 断路器

## 隔离

### 按依赖隔离资源 【推荐】

调用多个下游时，每个下游使用独立的连接池或并发上限，关键业务和非关键业务使用不同的资源池。容器资源限制、网关限流和独立队列已经能隔离时，不在应用代码中重写。每个分区都要单独监控。

**原因：** 共用资源池时，一个慢依赖会占满全部连接，其他依赖的请求也跟着失败。

**例外：** 资源利用率不能下降，或系统规模小到隔离没有收益时，不做隔离。

**来源：** Azure 舱壁

## 限流

### 针对最先饱和的资源设置限制 【推荐】

**适用：** 线上服务

先找出瓶颈，再选择限制维度。瓶颈是并发或下游容量时，按请求速率限制保护不了系统。不同操作的成本差异大时，按成本计量。阈值是否做成动态配置见 [配置](../architecture/configuration.md)。

**来源：** Azure 节流、Google SRE 过载处理

### 按调用方限制，并有意识地选择算法 【推荐】

按租户或调用方设置额度，避免单个调用方占满资源。

| 算法 | 特点 | 适用场景 |
|---|---|---|
| 令牌桶 | 允许一定突发 | 网关吸收短时峰值 |
| 漏桶 | 匀速放行 | 后端需要稳定流入 |
| 固定窗口 | 实现简单，窗口边界可能出现连续突发 | 精度要求低 |
| 滑动窗口 | 更平滑，状态更多 | 需要精确限制 |

多实例共享额度时，本地计数快但不精确，集中计数精确但增加延迟。需要集中计数的接口见 [审计与防滥用](../security/audit-and-abuse.md)。

**来源：** Azure 节流、Google SRE 过载处理

### 拒绝要明确且便宜 【推荐】

**适用：** 线上服务

超出调用方额度时返回 429，服务整体过载时返回 503，并尽量带上 `Retry-After`。全局和按 IP 的粗限流放在鉴权和解析之前，按用户、账号或租户的限流放在身份解析之后。

**原因：** 拒绝的成本接近正常处理时，被拒绝的请求仍然能压垮服务。

**来源：** Azure 节流、AWS 负载削减

### 调用受限服务时主动限速 【推荐】

批量任务调用有配额的下游时，自己控制发送速率，比发完再处理大量拒绝更高效。

**来源：** Azure 限速

## 降级

### 过载时优先保核心请求 【推荐】

接近过载时主动拒绝一部分请求，让接受的请求保持正常延迟。能区分优先级时，先拒绝低价值请求，下游调用沿用上游的优先级。

**原因：** 过载时吞吐量不会保持平稳，而是下降。全部接收的结果是全部超时。

**来源：** AWS 负载削减、Google SRE 过载处理

### 降级路径要简单且经过测试 【推荐】

**适用：** 线上服务

降级应当减少工作，比如隐藏推荐模块、返回缓存结果。不切换到另一条复杂链路。

很少运行的降级路径必须定期测试。

**原因：** 平时不运行的路径最容易隐藏缺陷，而且往往在最糟的时候才首次触发，可能把故障放大。

**来源：** AWS 回退策略、Google SRE 级联故障

### 降级结果不伪装成正常结果 【必须】

调用方要能知道结果不完整。不能把依赖失败改写成空数据返回。

## 背压

### 所有队列和缓冲都有上限 【必须】

**适用：** 线上服务

进程内队列、线程池队列和批处理缓冲都要限长，满了就拒绝。队列相对线程池要短。

**原因：** 无界队列只是把过载变成延迟和内存增长，请求排到时调用方早已放弃。

**来源：** Google SRE 级联故障

### 向上游传递过载信号 【推荐】

**适用：** 线上服务

下游返回 429 或 503 且重试耗尽时，如实向上传递，不改写成 500，让调用方知道需要减速。

**来源：** Azure 节流

### 异步管道要控制消费速率 【推荐】

队列只能削峰，不能解决长期入不敷出。监控队列深度和最老消息的年龄，平均生产速率持续超过消费速率时，要扩容或在生产端减量。扩容消费者时，要限制对下游的总速率。

消息本身的规则见 [消息](../async/messaging.md)。

**来源：** Azure 队列削峰、AWS 队列积压
