# 一致性

本文规定如何基于事实判断状态，并在并发和分布式环境下保持数据正确。事务细节见 [事务](../data/transactions.md)，消息投递见 [消息](../async/messaging.md)。

## 基于事实数据判断

### 判断逻辑贴近事实 【必须】

用实际数据判断状态，比如按时间戳比较新旧，目标端已有数据就跳过处理。不靠间接标记推断。

**原因：** 标记只是对事实的转述。写入中断、人工修数或并发都会让标记和实际数据不一致，而判断却继续基于错误的标记。

**示例：**

反例：

```sql
SELECT id FROM source_items WHERE synced = false;
```

正例：

```sql
INSERT INTO target_items (id, payload, updated_at)
VALUES (:id, :payload, :updated_at)
ON CONFLICT (id) DO UPDATE
SET payload = EXCLUDED.payload, updated_at = EXCLUDED.updated_at
WHERE target_items.updated_at < EXCLUDED.updated_at;
```

**来源：** 团队

### 比较用的时间戳来自同一权威来源 【必须】

比较新旧时，时间戳由数据的所有者生成，不混用不同机器的本地时钟。需要严格顺序时，使用所有者生成的递增序号。

**原因：** 不同机器的时钟可能不一致甚至回跳。

**来源：** Kleppmann 分布式锁

## 幂等

关键写操作的请求标识见 [rest.md](../api/rest.md)。

### 有副作用的操作设计成幂等 【必须】

可能被重试、重放或重复投递的写操作，执行多次的效果和执行一次相同。

**原因：** 超时不代表对方没有执行，消息也通常至少投递一次，重复是常态。

**来源：** AWS 超时与重试、Azure 幂等消费者

### 优先依靠数据本身保证幂等 【推荐】

能用唯一约束、条件更新或“目标端已有就跳过”实现时，不额外维护去重记录。

### 重复请求返回语义相同的结果 【推荐】

识别出重复时，返回和首次成功相同含义的响应，不返回“已存在”这类错误。标识相同、参数不同时不当作重复处理，所以保存标识时要一并保存参数或其摘要。接口层的响应见 [rest.md](../api/rest.md)。

**来源：** AWS 幂等 API

### 去重记录和业务写入同一事务 【必须】

确实需要去重表时，标识和业务数据在同一事务中提交。分开提交时，崩溃会导致丢失处理或重复处理。多个消费者共用去重表时，键要包含消费者身份。

去重键用稳定的业务标识或生产者分配的消息标识，不用关联 ID。

**来源：** Azure 幂等消费者

## 并发控制

事务内不调用外部服务，见 [事务](../data/transactions.md)。

### 不用“先查后写”保证唯一性 【必须】

两个并发请求都可能通过检查。使用数据库唯一约束、条件更新或锁。

**示例：**

反例：

```sql
SELECT count(*) FROM users WHERE email = :email;
INSERT INTO users (email) VALUES (:email);
```

正例：

```sql
ALTER TABLE users ADD CONSTRAINT uk_users_email UNIQUE (email);
INSERT INTO users (email) VALUES (:email);
```

### 按冲突频率选择并发控制 【推荐】

| 方式 | 适用场景 | 注意 |
|---|---|---|
| 条件更新 | 单行简单修改 | 优先选择，根据影响行数判断结果 |
| 乐观锁（版本号） | 读改写间隔长，冲突少 | 冲突时重新读取再决定 |
| 悲观锁 | 冲突多，重做代价大 | 持锁时间要短，固定加锁顺序 |
| 分布式锁 | 跨数据源协调 | 最后才考虑 |

**示例：**

```sql
UPDATE inventory SET stock = stock - 1
WHERE sku_id = :sku_id AND stock >= 1;
```

## 分布式锁

### 先确认锁的用途 【推荐】

| 用途 | 锁失效的后果 | 要求 |
|---|---|---|
| 提高效率，避免重复工作 | 多做一次，代价小 | 简单实现即可 |
| 保证正确性 | 数据损坏 | 必须有存储层的保护 |

能用唯一约束或条件更新解决的，不引入分布式锁。

**来源：** Kleppmann 分布式锁

### 设置过期时间，只释放自己持有的锁 【必须】

锁必须有过期时间，防止持有者崩溃后永久占用。加锁时写入持有者的随机值，释放时用原子操作比较后再删除，避免删掉别人的锁。

### 锁不是唯一的正确性保证 【必须】

进程暂停或网络延迟时，持有者可能在锁过期后才继续写入。这时另一方已经拿到了锁。

正确性依赖锁时，写入要带递增的防护令牌，由存储端拒绝更小的令牌。数据库约束是最后一道防线。

**来源：** Kleppmann 分布式锁

## Outbox

中继可能在发送后、记录前崩溃，所以消息可能重复，消费者幂等见 [消息](../async/messaging.md)。中继用轮询实现最简单。

### 消息丢失不可接受时使用 Outbox 【推荐】

默认在事务提交后直接发送，并写明进程崩溃时可能丢消息。消息丢失不可接受时，先向用户说明，再使用 Outbox：业务数据和待发消息写入同一事务，由独立的中继进程投递。任何情况下都不在事务中发送。

**原因：** 事务内发送时，事务回滚后消息已经发出；提交后发送时，进程崩溃会丢消息。

**示例：**

```sql
BEGIN;
UPDATE orders SET status = 'paid' WHERE id = :id AND status = 'pending';
INSERT INTO outbox (id, topic, payload, created_at)
VALUES (:event_id, 'order.paid', :payload, :now);
COMMIT;
```

**来源：** microservices.io Outbox

## Saga

### 优先避免跨服务事务 【推荐】

需要 Saga 时，先检查服务边界。强一致的数据通常应该放在同一服务，见 [服务边界](../architecture/service-boundaries.md)。

Saga 把业务操作拆成多个本地事务，某一步失败时用补偿操作撤销前面的步骤。补偿针对业务上会正常发生的失败，比如库存不足。罕见技术故障不要为此增加补偿，见 [弹性设计](resilience.md)。

**来源：** Azure 微服务边界、Azure Saga

### 按步骤数选择协调方式 【推荐】

| 方式 | 适用场景 | 风险 |
|---|---|---|
| 协同（事件驱动） | 步骤少，参与方少 | 流程分散，难以追踪，可能循环依赖 |
| 编排（中心协调者） | 步骤多，流程复杂 | 协调者是新的故障点 |

**来源：** Azure Saga

### 把不可撤销的步骤放在后面 【推荐】

步骤分三类：可补偿、不可逆的关键步骤、关键步骤之后的可重试步骤。关键步骤成功后，后续步骤不能撤销，只能重试，所以它们必须幂等。重试耗尽后告警并人工处理。

**来源：** Azure Saga

### 处理 Saga 缺少隔离的问题 【必须】

本地事务已经提交，其他流程能看到中间状态，可能出现丢失更新和脏读。用“处理中”这类业务状态标明中间状态，更新前重新读取确认。补偿本身也可能失败，要有告警和处理方式。

**来源：** Azure Saga

## 最终一致性

### 明确可接受的延迟 【推荐】

使用最终一致时，写明数据最长多久一致、不一致期间用户看到什么，并监控实际延迟。异步处理未完成时显示“处理中”，不显示已成功。

### 消费者接受乱序 【推荐】

能不依赖顺序就不依赖。收到较旧的数据时按“判断逻辑贴近事实”比较后跳过。

**来源：** Azure 队列削峰
