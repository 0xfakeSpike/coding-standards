# 后端测试

本文讲后端特有的测试实践。测试分层和替身分类见 [testing-strategy.md](../general/testing-strategy.md)，测试框架见语言层，契约测试见 [contracts.md](api/contracts.md)。

## 集成测试

### 接口和存储逻辑写集成测试 【推荐】

覆盖请求解析、鉴权、事务和错误响应。这些问题发生在模块边界，单元测试发现不了。

**示例：**

| 场景 | 断言 |
|---|---|
| 未带令牌 | 401，不产生数据 |
| 访问他人资源 | 403 或 404 |
| 非法参数 | 4xx，错误结构符合契约 |
| 中途失败 | 事务回滚，数据无残留 |
| 重复请求 | 只产生一条记录 |

### 通过公开入口驱动测试 【推荐】

从 HTTP 或 RPC 入口发起请求，断言响应和持久化结果，不直接调用内部方法。

### 测试数据相互隔离 【推荐】

每个用例自己准备数据，用事务回滚、独立的库或唯一的业务键隔离，不依赖其他用例留下的数据。

**原因：** 共享数据会让测试依赖执行顺序，也无法并行。

**来源：** Fowler 消除不确定性

### 异步结果用带超时的轮询断言 【推荐】

消息消费和后台任务的结果用轮询等待，不写固定时长的等待。

**来源：** Fowler 消除不确定性

## Testcontainers

### 数据库相关逻辑用真实数据库测试 【推荐】

用 Testcontainers 启动与生产相同类型和版本的数据库、缓存和消息队列。

**原因：** 内存数据库的 SQL 方言和事务行为可能与生产不同。

**来源：** Testcontainers 文档

### 镜像写明标签 【推荐】

镜像标签与生产版本一致，不用 `latest`。

**示例：**

反例：

```text
postgres:latest
```

正例：

```text
postgres:17.2-alpine
```

**原因：** 浮动标签让测试结果随时间变化。

### 不硬编码地址和端口 【推荐】

容器端口映射到宿主机的随机端口，地址也可能不是 `localhost`。连接信息在容器启动后读取，再注入应用配置。

**原因：** 固定端口会与本地服务或并行测试冲突，部分 CI 环境也无法通过 `localhost` 访问。

**来源：** Testcontainers 文档

### 配置就绪等待策略 【推荐】

端口可以连接不代表服务已就绪。根据依赖选择日志、HTTP 或健康检查等待，并按需调整启动超时。

**来源：** Testcontainers 文档

### 同一测试套件共享容器 【推荐】

容器启动慢，整个测试运行期间只启动一次，由 Testcontainers 负责清理。用例之间靠清理数据或独立的库隔离。

**来源：** Testcontainers 文档

### CI 不使用可复用容器 【推荐】

**适用：** 多人协作

可复用容器是实验特性，只用于本地开发提速。它在测试结束后不会停止，状态可能带到下次运行。

**来源：** Testcontainers 文档

## 第三方替身

### 第三方服务在客户端层替换 【推荐】

业务代码依赖自己定义的客户端接口，测试时替换它。需要验证序列化和错误映射时，用本地 HTTP 替身服务测试客户端本身。

**工具：** WireMock

### 替身覆盖失败场景 【推荐】

除成功响应外，还要覆盖超时、连接中断、限流、5xx 和格式错误的响应，并断言重试、降级和错误映射的行为。

**示例：**

| 替身行为 | 期望 |
|---|---|
| 延迟超过超时时间 | 按时失败，不阻塞 |
| 返回 503 | 按策略重试，次数有上限 |
| 返回 400 | 不重试 |
| 响应缺字段 | 返回明确错误，不写入脏数据 |

### 自动化测试不调用真实第三方 【必须】

真实服务的限流、数据变化和网络问题会造成不稳定，还可能产生费用。验证真实连通性用少量独立运行的冒烟测试。

**来源：** Fowler 消除不确定性

### 替身与真实行为保持一致 【推荐】

替身的数据来自真实响应样本或对方的契约，并配合契约测试校验，否则替身可能与真实服务不一致。

**来源：** Fowler 消除不确定性、Pact 文档

## 迁移测试

CI 在真实类型的空数据库上执行全部迁移，见 [migrations.md](data/migrations.md)。

### 集成测试使用迁移建出的表结构 【推荐】

不用 ORM 自动建表或单独维护的 SQL 文件代替迁移。

**原因：** 否则测试验证的表结构与生产不同。

### 校验迁移结果与代码一致 【推荐】

迁移后比较实际表结构和模型定义，有差异时让 CI 失败。

### 数据变更迁移用代表性数据验证 【推荐】

迁移会修改已有数据时，准备包含空值、边界值的数据，断言迁移后的结果。大表变更要在接近生产的数据量上测量耗时和锁影响。

## 性能测试

压测的环境、数据和发压方式见 [性能](reliability/performance.md)。

### 先定义目标再测试 【推荐】

写明场景、并发或到达速率、数据规模和通过标准，比如 P99 小于 300 毫秒、错误率小于 0.1%。没有目标时，结果无法判断。测量方法见 [performance.md](../general/performance.md)，压测和容量治理见 [performance.md](reliability/performance.md)。

**示例：**

| 项目 | 取值 |
|---|---|
| 场景 | 创建订单 |
| 负载 | 200 请求每秒，持续 15 分钟 |
| 数据 | 1000 万订单 |
| 通过标准 | P99 小于 300 毫秒，错误率小于 0.1% |

### 看分位数和错误率 【推荐】

报告 P50、P95、P99、吞吐量和错误率，不只看平均值。同时记录 CPU、内存、连接池和队列积压，找到瓶颈。

### 排除预热影响 【推荐】

预热阶段不计入结果，运行时间足够长，让缓存和连接池进入稳定状态。

### 与基线比较 【推荐】

保存每次的结果，在相同环境下比较。关键接口定期运行，及时发现退化。

### 不直接压测生产和第三方 【必须】

压测在隔离环境运行，第三方依赖用替身。替身要模拟真实的延迟。

**例外：** 确需在生产压测时，提前评审，使用隔离的测试数据，并准备好停止手段。
