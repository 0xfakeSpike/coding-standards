# Agent 工程规范

本文规定 Agent 服务的分层、失败处理、工具、上下文、成本和安全。通用错误原则见 [错误处理原则](../../general/error-handling.md)，通用重试和超时见 [弹性设计](../reliability/resilience.md)，检索增强见 [RAG](rag.md)。

## 分层

### 先用最简单的方案 【推荐】

能用单次模型调用加检索解决的，不做 Agent。步骤固定的任务用代码编排，只有步骤数无法预知时才让模型决定流程。多 Agent 只用于可并行、彼此依赖少的任务，子 Agent 只向上返回精简摘要。

**原因：** Agent 用延迟和成本换效果，多 Agent 的 token 消耗更高，错误还会逐步累积。

**来源：** Anthropic Building Effective Agents、Anthropic 多智能体系统

### 按职责分层 【推荐】

| 层 | 职责 | 不做 |
|---|---|---|
| 编排 | 驱动循环，决定下一步，判断停止 | 不写工具实现 |
| 模型调用 | 组装请求，解析响应，隔离 SDK 或框架 | 不做业务判断 |
| 工具 | 校验参数，执行，返回结果 | 不感知循环状态 |
| 存储 | 持久化运行记录 | 不含决策逻辑 |

使用框架时，要清楚它实际发给模型的内容，框架类型不越过模型调用层。

**来源：** Anthropic Building Effective Agents

## 工具调用失败处理

### 工具失败不拖垮进程 【必须】

工具执行的失败都在工具层捕获，转换成工具结果交回模型，进程和当前任务继续运行。结果要说明哪里失败、原因和下一步可以怎么做，不返回堆栈、内部标识或密钥。失败同时记录日志，程序缺陷仍要暴露和修复。

参数值不合法、下游接口失败、业务规则不满足都放在工具结果中。工具不存在、请求结构不合法这类模型难以自行修复的问题，工具服务端按所用协议的请求错误返回。Agent 循环收到协议错误，或发现模型调用了不存在的工具时，仍要合成一条错误工具结果写回，该调用才算闭环。

**原因：** 进程退出会中断所有进行中的任务，含糊的错误又让模型只能猜测。

**示例：**

```json
{"tool_call_id": "call_7", "status": "error", "error_type": "invalid_argument", "content": "出发日期必须晚于今天。今天是 2026-11-05，请修正 departure_date 后再调用。"}
```

**来源：** 团队、MCP 工具规范、Anthropic 工具调用处理、Anthropic 工具设计

### 每次工具调用都要闭环 【必须】

每个工具调用都设置超时，并在超时、取消、失败和工具不存在时也写回对应的结果。有副作用的工具超时后，结果写明“状态未知”，不写成“失败”，避免模型重复执行。

**原因：** 缺少结果的调用会破坏对话历史，后续模型调用可能直接报错。

**来源：** MCP 工具规范、Anthropic 工具调用处理

## 运行控制

### 残缺结果不当作成功 【必须】

模型调用失败或响应被截断时按失败处理，并记录错误类型。不把残缺响应当作成功结果。

### 循环必须有停止条件 【必须】

每次运行都限制最大步数、总耗时和 token 预算，超限时按失败结束，写明触发的限制。

**来源：** Anthropic Building Effective Agents、OWASP LLM Top 10

## 工具设计

### 少量边界清晰的工具 【推荐】

围绕任务设计工具，不逐个包装接口，多步操作可合并成一个工具。功能不重叠，工程师都分不清该用哪个时，模型也分不清。跨服务时用服务名和资源名作前缀。

**来源：** Anthropic 工具设计、Anthropic 上下文工程、Anthropic 工具定义

### 描述和参数不留歧义 【推荐】

描述写清用途、适用和不适用的场景、参数含义和限制。参数用明确的名字和严格的 Schema，例如 `user_id` 而不是 `user`。把容易出错的输入改掉，例如要求绝对路径。用多步骤且结果可验证的任务评估，重复的参数错误通常说明描述不清。

**原因：** 描述是影响工具效果的首要因素，措辞的小改动也会明显改变结果。

**来源：** Anthropic 工具定义、Anthropic 工具设计、Anthropic Building Effective Agents

### 返回高信号的有限结果 【推荐】

只返回模型下一步需要的字段，优先用有语义的稳定标识。大结果默认分页、过滤或截断，截断时提示如何缩小查询。

**来源：** Anthropic 工具设计、Anthropic 工具定义

## 上下文管理

### 按需加载并主动压缩 【推荐】

上下文中保留路径、链接、查询条件这类轻量引用，需要时再用工具读取。长任务先清理不再需要的原始工具结果，接近上限时压缩成摘要，优先保证不漏关键信息。跨窗口的进度写入外部笔记。

**来源：** Anthropic 上下文工程

## 成本和可观测性

### 按 GenAI 语义约定埋点 【推荐】

一次运行、模型调用、工具调用都生成 span，名称分别为 `invoke_agent {gen_ai.agent.name}`、`{gen_ai.operation.name} {gen_ai.request.model}`、`execute_tool {gen_ai.tool.name}`。至少记录 `gen_ai.conversation.id`、`gen_ai.request.model`、`gen_ai.response.finish_reasons`、`error.type`。其余要求见 [链路追踪](../observability/tracing.md)。

**来源：** OTel GenAI 语义约定

### 提示词和响应默认不进遥测 【必须】

消息内容、工具参数和结果可能含个人数据，默认不记录。排查需要时显式开启，并优先写入受控的外部存储。其余要求见 [隐私](../security/privacy.md)。

**来源：** OTel GenAI 语义约定、Anthropic 多智能体系统

### 统计并限制用量 【必须】

**适用：** 线上服务

记录 `gen_ai.usage.input_tokens`、`gen_ai.usage.output_tokens` 和缓存 token，能按用户和会话汇总。设置请求频率、配额、输入大小和排队数量上限，并对异常消耗告警。

**原因：** 无上限的调用会造成费用失控和服务不可用。

**来源：** OWASP LLM Top 10、OTel GenAI 语义约定

## 提示注入防护

提示注入无法彻底防止，防护的目标是限制注入成功后的影响。通用注入防护见 [输入与注入](../security/input-and-injection.md)。

### 外部内容一律当作数据 【必须】

网页、邮件、上传文件、第三方接口和检索内容都不可信，放在工具结果中并明确标识，不拼进系统提示，持久化后再次使用时同样按不可信内容处理。定期用直接注入和间接注入做对抗测试。

**来源：** OWASP LLM Top 10、Anthropic 工具调用处理

### 权限在代码中强制 【必须】

只给任务需要的工具和操作，不提供任意命令或任意 URL 这类开放工具。工具以当前用户身份执行，授权由下游系统判定，密钥不进入提示词。删除、外发、付款这类操作在执行前展示参数，由用户确认，模型不能跳过。其余要求见 [授权](../security/authorization.md)。

**来源：** OWASP LLM Top 10、MCP 工具规范

### 模型输出按不可信输入处理 【必须】

模型输出进入下游前，用确定性代码校验格式，按使用场景编码，数据库操作使用参数化查询。

**来源：** OWASP LLM Top 10
