# 消息

本文讲基于消息队列的异步通信，以 Kafka 和 RabbitMQ 为主。写库和发消息的一致性（Outbox）见 [consistency.md](../reliability/consistency.md)，任务队列见 [background-jobs.md](background-jobs.md)。

## 投递语义

### 按至少一次投递设计 【必须】

消息进入代理之后默认按至少一次设计：不丢，但可能重复。提交业务数据到消息进入代理之间的取舍见 [consistency.md](../reliability/consistency.md) 的 Outbox。不依赖中间件宣称的恰好一次。

| 语义 | 含义 | 适用 |
|---|---|---|
| 至多一次 | 可能丢失，不重复 | 可以丢失的监控采样 |
| 至少一次 | 不丢失，可能重复 | 默认选择 |
| 恰好一次 | 只处理一次 | 只在特定范围内成立 |

**原因：** 生产者收不到确认时只能重发，消费者处理完、提交前崩溃也会重新收到。Kafka 的恰好一次限于读写都在 Kafka 内的场景，写外部系统需要该系统配合。

**来源：** Kafka 文档、RabbitMQ 文档

### 发送方确认消息已被接收 【必须】

发送后等待代理确认，未确认的消息要重发。不用“发出去就算成功”的模式发送重要消息。

| 中间件 | 配置 |
|---|---|
| Kafka | `acks=all`，配置 `min.insync.replicas`，关闭不干净的领导者选举 |
| RabbitMQ | 开启发布确认，使用持久队列和持久消息 |

**原因：** 重发会产生重复，由消费者的幂等处理兜底。没有确认的话，代理崩溃时可能丢失尚未落盘的消息。

**来源：** Kafka 文档、RabbitMQ 文档

### 处理完成后再确认 【必须】

消费者先完成处理，再提交位点或发送 ack。RabbitMQ 不用自动确认模式处理重要消息。

**原因：** 先确认后处理时，消费者崩溃就会丢消息。RabbitMQ 的自动确认还没有未确认数量的上限，消费者可能被压垮。

**来源：** Kafka 文档、RabbitMQ 文档

## 幂等消费

### 消费者保持幂等 【必须】

同一条消息处理多次，结果和处理一次相同。优先让操作本身幂等，比如条件更新或按业务键写入。做不到时用消息 ID 去重。幂等的通用做法见 [consistency.md](../reliability/consistency.md)。

**示例：**

反例：每次收到消息都累加。

```sql
UPDATE accounts SET balance = balance + 100 WHERE id = ?;
```

正例：去重记录和业务写入放在同一个事务里，插入影响行数为 0 时跳过业务写入。

```sql
INSERT INTO processed_messages (message_id, consumer) VALUES (?, ?)
ON CONFLICT (message_id, consumer) DO NOTHING;
UPDATE accounts SET balance = balance + 100 WHERE id = ?;
```

示例是 PostgreSQL 语法，MySQL 用 `INSERT IGNORE`。RabbitMQ 的 `redelivered` 标记只说明消息可能处理过，不能代替幂等处理。

**来源：** RabbitMQ 文档

## 顺序

### 不假设全局有序 【必须】

Kafka 只保证单个分区内有序。RabbitMQ 的队列按发布顺序保存消息，但多个消费者并行处理和重新入队都会打乱观察到的顺序。

**来源：** Kafka 文档、RabbitMQ 文档

### 需要顺序时按业务键分区 【推荐】

同一实体的消息必须有序时，Kafka 用实体 ID 作为消息键，使其进入同一个分区。RabbitMQ 用单活跃消费者。这两种方式都会限制这部分数据的并行度。

**来源：** Kafka 文档、RabbitMQ 文档

### 无法保证顺序时让消费者判断 【推荐】

消息带序列号或业务时间，消费者与已处理的值比较，丢弃过期的消息。

**来源：** Azure 后台任务

## 重试和死信

### 区分暂时失败和永久失败 【必须】

下游超时这类暂时失败走重试。格式错误这类永久失败不重试，直接进入死信。引用数据不存在可能只是乱序或复制延迟，先按暂时失败有限次重试，耗尽后进入死信。

**原因：** 永久失败重试多少次都不会成功，只会占用资源。

**来源：** Azure 后台任务

### 失败消息有重试上限和死信队列 【必须】

**适用：** 线上服务

重试次数有上限，并使用退避。超过上限的消息进入死信队列，记录失败原因，并配置告警。死信要有人处理，不能只堆积。

**原因：** 反复失败的消息会阻塞队列，或者无限循环消耗资源。

**工具：** 对死信数量和最老消息的年龄配置告警，见 [metrics-and-alerts.md](../observability/metrics-and-alerts.md)。

**来源：** Azure 竞争消费者、Azure 后台任务

### 死信消息可以重新投递 【推荐】

修复问题后，死信消息要能重新投回原队列。消息中保留原始内容、失败原因和重试次数。重放依赖消费者的幂等处理。

## 消息格式

### 消息带统一的元数据 【推荐】

所有消息使用同一种信封，包含唯一 ID、类型、发生时间和追踪 ID。业务内容放在 `data` 中。

**示例：**

```json
{
  "message_id": "01J9ZK3Q7X8Y",
  "type": "order.paid",
  "occurred_at": "2026-11-05T08:30:00Z",
  "trace_id": "a1b2c3",
  "data": {
    "order_id": "1001",
    "paid_at": "2026-11-05T08:30:00Z"
  }
}
```

### 事件名描述已经发生的事 【推荐】

事件用过去式，格式为 `实体.动作`，比如 `order.paid`。命令用祈使语义，比如 `order.close`。

### 消息体保持精简 【推荐】

只放消费者需要的字段。大对象放到对象存储，消息里放引用。消息不含密码、Token 等敏感信息，个人信息按 [privacy.md](../security/privacy.md) 处理。

## Kafka 要点

### 按消费并行度规划分区 【推荐】

同一消费者组内，一个分区同一时刻只由一个消费者处理，消费者数量超过分区数时多余的会空闲。

| 项目 | 做法 |
|---|---|
| 消息键 | 需要局部有序时使用实体 ID，注意避免数据倾斜 |
| 持久性 | 接受 `acks=all` 的延迟，换取已提交消息不丢 |
| 事务消费 | 使用 Kafka 事务时，消费者设 `isolation.level=read_committed` 并关闭自动提交 |
| 死信 | 消费者组没有内置死信，由应用转发到死信主题 |

**来源：** Kafka 文档

### 单批处理时间受控 【必须】

Kafka 消费者两次拉取的间隔不能超过 `max.poll.interval.ms`，否则会被踢出组并触发再均衡，已处理未提交的消息会重复。耗时任务减小批量，或者转给任务队列。

### 监控消费积压 【必须】

**适用：** 线上服务

监控 Kafka 的消费延迟（lag）和 RabbitMQ 的队列长度，积压持续增长时告警。

## RabbitMQ 要点

### 使用仲裁队列并限制预取 【推荐】

| 项目 | 做法 |
|---|---|
| 队列类型 | 重要数据用仲裁队列（quorum queue）并复制 |
| 预取 | 设置有上限的 `prefetch`，几百已经足够，过大没有吞吐收益 |
| 投递上限 | 配置 `delivery-limit`，超过后丢弃或进入死信，所以必须同时配置死信 |
| 死信可靠性 | 默认的死信转发不带确认，可能丢失；仲裁队列支持至少一次死信 |
| 确认超时 | 默认 30 分钟未确认会重新投递，长任务要调整 |
| 连接 | 开启心跳，及时发现断开的连接 |

**来源：** RabbitMQ 文档
