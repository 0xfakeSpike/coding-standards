# 服务边界

本文规定模块和服务如何划分、如何通信、数据归谁所有。模块内部的分层见 [layering.md](layering.md)。通用的职责划分原则见 [职能划分](../../general/responsibilities.md)。

## 组件职责

### 模块边界清楚，职责单一，不越界 【必须】

每个模块都能用一句话说清负责什么。模块只做这句话内的事，不替其他模块做事，也不伸手进入其他模块的内部。

**原因：** 边界模糊后，一个改动的影响范围无法判断，模块也无法单独理解和测试。

**示例：** 通知模块只负责把消息发出去。“什么情况下该通知”由触发方的业务模块决定，不写进通知模块。

**来源：** 团队

### 每个模块自己负责自己的状态 【推荐】

模块不依赖其他模块顺带完成自己的工作。需要什么由模块自己检查、自己触发。详见 [职能划分](../../general/responsibilities.md)。

### 按业务能力划分，不按技术层划分 【推荐】

模块和服务围绕业务能力组织，比如订单、支付，不拆成“数据服务”“校验服务”这类技术切片。一个模块不跨限界上下文，模块内混入两套领域模型时，先调整模型。

**原因：** 按技术切分时，一个需求要同时改多个模块，也要多个团队协调。

**来源：** Fowler 微服务、Azure 微服务边界

## 模块化单体

### 优先模块化单体 【推荐】

新系统默认做成一个部署单元，内部严格分模块。边界稳定、有明确需求后再拆分。

**原因：** 早期难以划准边界，而在服务之间移动功能的代价远高于在模块之间移动。微服务还要额外承担分布式调用、最终一致和运维的成本。

**例外：** 团队已有成熟的微服务经验，且边界已被现有系统验证过。

**来源：** Fowler MonolithFirst、Fowler 微服务溢价

### 模块之间只走公开接口 【推荐】

模块对外暴露明确的接口，其余都是内部实现。其他模块不引用内部类型，不访问内部的表。

**原因：** 单体没有进程隔离，边界只靠约定时会逐渐失效。

**工具：** 在 CI 中用依赖检查工具禁止跨模块引用内部目录。

**来源：** Fowler 微服务权衡

### 模块的数据也要隔离 【推荐】

单体内每张表只属于一个模块。其他模块需要数据时调用该模块的接口，不跨模块 JOIN。

**例外：** 跨业务的列表和报表查询放在专门的只读模块，只查询不写入。数据量大时再考虑只读副本或汇总表。

**来源：** microservices.io 每服务一库

## 服务拆分

### 拆分要有具体理由 【推荐】

只有满足下列至少一项，并且模块化单体已经解决不了时才拆分：

| 理由 | 判断方式 |
|---|---|
| 独立扩缩容 | 资源需求差异大，整体扩容浪费明显 |
| 团队边界 | 多个团队在同一部署单元内互相阻塞 |
| 故障隔离 | 某部分的故障不能影响核心流程 |
| 独立发布节奏 | 发布频率差异大，合并发布成本高 |
| 安全或合规隔离 | 敏感数据需要单独的访问边界 |

“微服务更先进”“代码量大了”不是理由。

**原因：** 分布式带来的远程调用失败、最终一致和运维负担是确定的成本，收益必须大于它。

**来源：** Fowler 微服务溢价、Fowler 微服务权衡

### 检查拆分结果 【推荐】

拆分方案要能通过以下检查：

- 每个服务职责单一，一个小团队能独立维护。
- 服务之间没有频繁的细粒度调用。
- 可以单独部署，不需要同时发布其他服务。
- 不存在强一致要求被拆到两个服务的情况。

两个服务总是一起修改、调用频繁时，说明它们应该合并。

**来源：** Azure 微服务边界

## 数据归属

### 每份数据只有一个所有者 【推荐】

只有所有者服务可以写自己的数据，其他服务通过接口或事件获取。

**原因：** 多个服务写同一张表时，表结构的任何修改都要跨团队协调，运行时也互相干扰。

**工具：** 用独立的数据库账号和授权实施边界，不靠约定。

**来源：** microservices.io 每服务一库、microservices.io 共享数据库

### 按需选择隔离程度 【推荐】

| 方式 | 成本 | 适用场景 |
|---|---|---|
| 私有表 | 最低 | 服务少，共用一个实例 |
| 独立 Schema | 低 | 归属需要更清楚 |
| 独立数据库实例 | 高 | 吞吐量大或需要资源隔离 |

**来源：** microservices.io 每服务一库

### 跨服务查询有明确方案 【推荐】

| 方式 | 适用场景 | 代价 |
|---|---|---|
| 调用方组合接口结果 | 数据量小，实时性要求高 | 多次调用，依赖多个服务的可用性 |
| 订阅事件维护本地只读副本 | 查询频繁，能接受延迟 | 数据冗余，要处理延迟 |

跨服务的写操作见 [一致性](../reliability/consistency.md)。

**来源：** microservices.io 每服务一库、Fowler 事件驱动

## 服务间通信

### 按调用方是否需要立即结果选择方式 【推荐】

| 方式 | 适用场景 | 风险 |
|---|---|---|
| 同步调用（HTTP、gRPC） | 调用方必须拿到结果才能继续 | 可用性和延迟逐级相乘 |
| 异步消息 | 调用方不需要等待结果 | 需要处理重复、乱序和积压 |

**来源：** Azure 服务间通信

### 避免长的同步调用链 【推荐】

用户请求路径上的同步调用链要尽量短。把不需要立即完成的部分改成异步，或者重新划分边界。

**原因：** 每多一跳都会增加延迟，链路上任一环节不可用，整个请求就失败。

**来源：** Fowler 微服务、Azure 服务间通信

### 远程调用使用粗粒度接口 【推荐】

远程调用比进程内调用贵得多，一次调用完成一件完整的事，不把本地对象的读写方法直接暴露成远程接口。业务逻辑留在服务内，消息中间件只负责传递。

**来源：** Fowler 微服务、Azure 频繁 I/O

### 每个远程调用都按会失败处理 【必须】

超时、重试和熔断规则见 [弹性设计](../reliability/resilience.md)。接口设计见 [REST 接口](../api/rest.md) 和 [gRPC](../api/grpc.md)，消息见 [消息](../async/messaging.md)。

## API 网关

### 网关只做横切工作 【推荐】

| 适合放在网关 | 不放在网关 |
|---|---|
| 路由、TLS 终止 | 业务规则 |
| 身份校验、客户端限流 | 业务状态判断 |
| 请求日志、简单的响应聚合 | 跨服务事务编排 |

**原因：** 网关是所有请求的共同路径，放入业务逻辑后，会变成所有团队都要改的新单体。

**来源：** Azure API 网关、Fowler 微服务

### 网关不是唯一防线，也不能成为单点 【必须】

**适用：** 线上服务

网关完成身份校验后，服务内部仍要做权限判断，见 [授权](../security/authorization.md)。后端服务不直接暴露到公网。网关要部署多实例。

**来源：** Azure 网关路由

### 服务很少时不引入网关 【推荐】

只有一两个服务时，网关只增加一跳和一个运维对象。不同类型的客户端需求差异很大时，才考虑为每类客户端单独设网关（BFF）。

**来源：** Azure 网关路由、microservices.io API 网关

## 反模式

### 识别常见反模式 【推荐】

| 反模式 | 信号 | 处理 |
|---|---|---|
| 分布式单体 | 一个需求要同时发布多个服务 | 重新划分边界或合并 |
| 共享数据库 | 多个服务读写同一张表 | 明确所有者，其他方走接口 |
| 频繁互调 | 完成一次操作要来回调用多次 | 合并服务或改用粗粒度接口 |
| 按技术层拆服务 | 存在只做增删改查的数据服务 | 按业务能力重新组织 |
| 公共业务库 | 多个服务依赖一个包含业务规则的共享库 | 把规则收回所属服务 |
| 万能网关 | 业务判断写在网关配置或脚本里 | 移回所属服务 |

**来源：** Azure 微服务边界、microservices.io 共享数据库
