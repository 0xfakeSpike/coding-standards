# 分层架构

本文规定后端代码的分层、依赖方向和层间数据转换。层名因语言和框架而异，重点是职责划分。模块之间的边界见 [service-boundaries.md](service-boundaries.md)，领域模型见 [domain-modeling.md](domain-modeling.md)。

## 选位置

### 改动放在最该放的位置 【必须】

动手前先评估这段逻辑最该属于哪一层、哪个模块。不能因为“现在这里能做”就做在这里。

**原因：** 就近塞入的逻辑会让职责逐渐混杂，之后每次修改都要先分辨它为什么在这里。

**示例：** 接口响应缺一个字段时，不在控制器里临时查询补上。先判断这个数据属于哪个业务模块，再由该模块提供。

**来源：** 团队

### 按职责分层，依赖单向 【必须】

| 层 | 职责 | 不做什么 |
|---|---|---|
| 接口层（Controller、Handler） | 解析请求、校验参数格式、调用应用层、转换响应 | 不写业务规则，不直接访问数据库 |
| 应用层（Service、Use Case） | 编排用例、划定事务边界 | 不依赖 HTTP 等传输层对象 |
| 领域层（实体、领域服务） | 业务规则和不变量 | 不依赖框架、数据库和外部系统 |
| 数据访问层（Repository、DAO） | 读写数据 | 不写业务判断 |
| 外部客户端（Client、Gateway） | 封装第三方调用 | 不把第三方类型暴露给业务代码 |

业务简单时，应用层和领域层可以合并，只转发调用的层应当去掉。但业务规则不能下沉到数据访问层，也不能上浮到接口层。

**原因：** 层次混杂后，业务规则无法脱离框架和数据库测试，同一规则也容易在多个入口各写一份。

**工具：** 在 CI 中用依赖检查工具校验层间引用。

**来源：** Martin 整洁架构

## 业务逻辑与数据库

业务逻辑不放数据库，见 [表结构设计](../data/schema-design.md)。

### 数据库不做展示加工 【推荐】

字符串拼接、格式转换和复杂计算放到应用层。数据库难以水平扩展，把算力花在这些工作上会挤占读写能力。聚合、过滤和排序这类数据库擅长的操作保留在数据库。

**来源：** Azure 繁忙数据库

## 依赖方向

### 依赖指向业务核心 【推荐】

源码依赖只能从外层指向内层。业务代码不引用框架类型、数据库驱动和第三方 SDK。业务代码需要外部能力时，定义自己需要的接口，由外层实现。

**原因：** 依赖反过来时，更换数据库或第三方服务会波及业务规则。

**示例：**

| 写法 | 判断 |
|---|---|
| 领域层引用 ORM 的行对象 | 反例 |
| 应用层接收框架的请求对象 | 反例 |
| 应用层声明“支付网关”接口，外部客户端实现它 | 正例 |

**来源：** Martin 整洁架构、Cockburn 六边形架构

### 依赖由外部传入 【推荐】

业务代码不直接创建数据库连接和外部客户端。依赖通过框架的依赖注入或构造参数传入，组装集中在程序入口。

**原因：** 内部创建的依赖无法在测试中替换，也无法统一配置超时和连接池。

### 用端口隔离外部世界 【推荐】

六边形架构把系统分成内外两侧。内侧是应用，外侧是用户、测试、数据库和第三方系统。

| 概念 | 含义 | 示例 |
|---|---|---|
| 端口 | 应用定义的一段有明确目的的对话 | “保存订单”“发送通知” |
| 驱动侧适配器 | 把外部输入转换成对应用的调用 | HTTP 处理器、消息消费者、测试用例 |
| 被驱动侧适配器 | 把应用的调用转换成具体技术 | SQL 实现、邮件服务实现 |

判断标准是业务用例能否不启动 HTTP 服务和数据库就运行。端口按业务目的命名，不按技术命名。

整洁架构和六边形架构的共同要求是业务核心不知道外部技术，圈层数量和名字不是硬性要求。外部依赖只有一种实现且短期不会变化时，可以直接使用具体实现，见 [通用编码原则](../../general/principles.md)。

**来源：** Cockburn 六边形架构、Martin 整洁架构

## 数据映射

### 数据库实体不直接作为接口响应 【必须】

接口的请求和响应使用单独定义的 DTO 或 Schema，在接口层完成转换。

**原因：** 内部字段可能泄露，接口形状也会和表结构绑死。

**示例：**

反例：

```json
{
  "id": 1001,
  "password_hash": "$2b$12$abc",
  "deleted_flag": 0,
  "internal_note": "高风险用户"
}
```

正例：

```json
{
  "id": "1001",
  "displayName": "张三"
}
```

### 跨层传递简单数据结构 【推荐】

越过层边界的数据，形式由内层决定。数据库框架返回的行对象、第三方 SDK 的响应对象不向内传递，在适配代码中转换成内层类型。

**来源：** Martin 整洁架构

### 映射只做转换 【推荐】

DTO 映射只处理字段对应和格式转换，不做业务判断，不发起查询。同一对象的转换集中在一处。

## 错误边界

### 区分业务错误和系统错误 【必须】

| 类型 | 示例 | HTTP 状态 | 日志级别 |
|---|---|---|---|
| 业务错误 | 余额不足、参数错误 | 4xx | INFO 或 WARN |
| 系统错误 | 数据库不可用、代码缺陷 | 5xx | ERROR |

通用原则见 [错误处理原则](../../general/error-handling.md)，响应结构见 [REST 接口](../api/rest.md)。

### 在统一入口转换错误 【推荐】

业务代码只抛出或返回本模块的错误。全局错误处理器或中间件负责转换成响应，不在每个处理器重复编写。未知错误对外返回通用信息，对内记录完整上下文。

## 目录模板

### 优先按业务模块组织目录 【推荐】

顶层按业务模块划分，模块内再按层划分。不要把所有控制器、所有服务各放一个顶层目录。

**原因：** 需求通常沿业务模块变化，按模块组织时一次改动集中在一个目录，模块边界也看得见。

**示例：**

```text
src/
├── order/
│   ├── api/
│   ├── application/
│   ├── domain/
│   └── infrastructure/
├── payment/
│   ├── api/
│   ├── application/
│   ├── domain/
│   └── infrastructure/
└── main/
```

| 目录 | 内容 |
|---|---|
| `api` | 处理器、DTO、映射 |
| `application` | 用例和事务边界 |
| `domain` | 实体、值对象、领域服务、端口 |
| `infrastructure` | 数据访问实现、外部客户端 |
| `main` | 程序入口和依赖组装 |

小型服务可以省略模块内的子目录。各语言的目录习惯见语言层的项目结构文件。
