# 日志

本文规定后端日志的格式、级别、字段和保留。审计日志见 [审计与防滥用](../security/audit-and-abuse.md)，个人信息的总体要求见 [隐私](../security/privacy.md)。

## 结构化日志

服务日志写到标准输出，见 [容器](../../general/containers.md)。

### 使用结构化日志 【推荐】

**适用：** 线上服务

日志输出为 JSON 等结构化格式，用日志库记录，不用标准输出打印函数代替。消息模板保持固定，变量放进字段。

**原因：** 文本拼接的日志无法按字段检索和聚合，也更容易被注入。

**示例：**

```json
{
  "timestamp": "2026-11-05T08:30:12.345Z",
  "level": "ERROR",
  "service": "payment",
  "traceId": "4bf92f3577b34da6a3ce929d0e0e4736",
  "message": "支付回调处理失败",
  "orderId": "1001",
  "error": "gateway timeout"
}
```

**来源：** OWASP 日志速查表

### 日志失败不影响业务 【必须】

**适用：** 线上服务

日志系统不可用时，业务请求继续处理，不能崩溃，也不能阻塞在写日志上。

**来源：** OWASP 日志速查表

## 级别

同一错误只记录一次，见 [错误处理原则](../../general/error-handling.md)。

### 按处理方式选择级别 【推荐】

| 级别 | 用途 | 示例 |
|---|---|---|
| ERROR | 需要人工关注的失败 | 数据库不可用、代码缺陷 |
| WARN | 异常但能自动恢复 | 重试成功、降级生效 |
| INFO | 关键业务事件 | 订单创建、服务启动 |
| DEBUG | 排障细节，生产默认关闭 | 中间计算结果 |

业务错误记 INFO 或 WARN，系统错误记 ERROR，分类见 [分层架构](../architecture/layering.md)。

**原因：** 把用户输入错误记成 ERROR，真正的故障就会被淹没。

### 高频路径不打大量 INFO 【推荐】

循环内和每秒执行多次的路径不逐条记录。需要了解频率时用指标，见 [指标和告警](metrics-and-alerts.md)。

### 运行时可调整级别 【推荐】

排障时能临时打开 DEBUG，不需要重新发布，并且到时自动恢复。

## 字段规范

### 每条日志包含基础字段 【推荐】

| 字段 | 含义 | 要求 |
|---|---|---|
| `timestamp` | 事件时间 | ISO 8601，UTC |
| `level` | 级别 | 全项目统一取值 |
| `service` | 服务名 | 与链路追踪的服务名一致 |
| `traceId` | 链路标识 | 有链路上下文时写入 |
| `message` | 事件描述 | 固定文本 |

可选字段包括 `spanId`、`version`、`host`、`userId`、`error`、`durationMs`。

**来源：** OWASP 日志速查表、OpenTelemetry 日志规范

### 能回答何时、何地、何人、何事 【推荐】

关键事件要能说清发生时间、发生位置、发起者和结果。系统记录时间和事件发生时间不同时分别记录。各节点时钟要保持同步，否则跨服务日志的先后顺序不可信。

**来源：** OWASP 日志速查表

### 字段名全局统一 【推荐】

同一含义在所有服务用同一个字段名和类型，比如都用 `orderId`，不混用 `order_id`、`oid`。

**原因：** 字段名不一致时，无法跨服务检索。

**来源：** OWASP 日志速查表

### 日志关联链路 【推荐】

有链路上下文时写入 `traceId`，这样才能从日志跳到链路。接入追踪库时由它自动注入，不手工传递。详见 [链路追踪](tracing.md)。

**来源：** OpenTelemetry 日志规范

### 错误日志带上下文 【推荐】

记录失败的操作、对象和原因，保留堆栈。只写“操作失败”的日志无法排查。

## 脱敏

### 禁止记录的内容 【必须】

下列内容不写入日志：

- 密码、Token、API Key、加密密钥、含凭据的连接串
- 完整银行卡号和证件号
- 无法律依据收集的数据

**原因：** 日志的访问范围比业务库宽，保留时间也更长，泄露后难以彻底清除。

**工具：** 在日志库中配置字段过滤器，并在测试中断言敏感字段不出现。

**来源：** OWASP 日志速查表

### 个人和敏感数据先处理再记录 【必须】

| 数据 | 处理方式 |
|---|---|
| 手机号、邮箱 | 掩码，比如 `138****0000` |
| 会话标识 | 哈希，仍能关联同一会话 |
| 用户标识 | 能满足排查时使用内部 ID，不用姓名 |
| 内部地址和文件路径 | 谨慎记录，不对外暴露 |

**示例：**

反例：

```json
{ "message": "登录失败", "phone": "13800000000", "password": "abc123" }
```

正例：

```json
{ "message": "登录失败", "phone": "138****0000", "reason": "invalid_credentials" }
```

**来源：** OWASP 日志速查表

### 不记录完整的请求和响应 【必须】

默认不记录请求体、响应体和完整请求头。确实需要时，用白名单指定字段。

**原因：** 黑名单总会漏，请求头和请求体是敏感数据最集中的地方。

### 防止日志注入 【必须】

用户输入写入日志前，处理换行符和分隔符，并限制长度。结构化输出和固定消息模板能阻止大部分问题。

**来源：** OWASP 日志速查表

## 采样

### 错误和安全事件不采样 【推荐】

**适用：** 线上服务

ERROR、WARN 和安全相关事件全量保留，只对高频且内容重复的 INFO 和 DEBUG 采样。

**原因：** 采样掉的错误无法追回，而认证失败这类事件的价值恰恰在频率。

### 采样保持链路完整，并限制总量 【推荐】

INFO 和 DEBUG 按 `traceId` 决定采样，同一请求的这类日志要么都留，要么都不留。ERROR、WARN 和安全事件绕过采样。单条日志和单实例的输出速率都要有上限，防止故障时日志洪水耗尽磁盘或收集通道。达到上限时优先丢弃低级别日志，并记录丢弃数量。

**来源：** OWASP 日志速查表

## 保留策略

### 保留期由法律、合同和排障需要决定 【必须】

**适用：** 高风险

按日志类型明确保留期，到期删除。不提前销毁，也不无限期保留。安全和审计日志按法规和合同要求，应用日志按排障需要。

**来源：** OWASP 日志速查表

### 限制日志访问 【必须】

**适用：** 高风险

日志平台按最小权限授权，日志不放在 Web 可访问的位置。

**来源：** OWASP 日志速查表
