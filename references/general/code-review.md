# 代码评审

## 作者

**适用：** 多人协作（本节全部规则）

### PR 只做一件自洽的事 【必须】

约 100 行是合理规模，约 1000 行通常过大。文件数也算规模：改动分散到很多文件时，同样难以评审。

**例外：** 删除代码可以放宽，删除整个文件的评审成本很低。

**来源：** Google 评审规范

### 测试与逻辑放在同一 PR 【必须】

重构和功能的拆分见 [refactoring.md](refactoring.md)。新增接口时，同一 PR 中要有实际用法。

**来源：** Google 评审规范

### 描述写清改动和原因 【必须】

包括改了什么、为什么改、如何验证、有什么风险。

**来源：** Google 评审规范

### 提交前先看一遍 diff 【推荐】

自查调试代码、无关改动和遗漏的测试。

### 解释落到代码或文档 【必须】

评审中需要解释的内容，要改进代码或写入项目文档，不只留在评审工具里。

**来源：** 团队、Google 评审规范

## 评审者

### 代码健康度确有改善即可批准 【必须】

**适用：** 多人协作

不追求完美，但明显恶化代码健康度的改动不能合入。

**来源：** Google 评审规范

### 按优先级评审 【推荐】

**适用：** 多人协作

1. 设计：职责和层次是否合理，改动是否放在最优位置。
2. 功能：逻辑、边界条件和并发。
3. 安全：权限、输入和敏感数据。
4. 复杂度：是否过度设计，是否有无用代码。
5. 测试：出错时能否失败。
6. 命名和风格：能交给工具的不靠人工。

**来源：** Google 评审规范、团队

### 高风险改动做专项安全审查 【必须】

**适用：** 高风险

涉及以下内容时，对照 [后端安全规范](../backend/index.md) 和 [前端安全规范](../frontend/security.md) 逐项检查，并在 PR 描述中写明结果：

- 认证和授权。
- 支付和资金。
- 加解密和密钥。
- 文件上传和文件路径。
- 由用户输入拼出的查询、命令或外部 URL。
- 敏感数据的存储和传输。

### 看不懂就要求澄清 【必须】

**适用：** 多人协作

评审者看不懂，以后的读者也看不懂。

**来源：** Google 评审规范

### 风格分歧看规范 【必须】

**适用：** 多人协作

风格以规范为准，个人偏好不阻塞合入。

**来源：** Google 评审规范
