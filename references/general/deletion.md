# 删除

没用的东西直接删。版本控制保留了历史，不需要为“以后可能用到”保留。

### 无用的都删 【必须】

确认没有使用方的代码、逻辑、配置和文件都要删除。

**原因：** 无用内容会误导读者，增加每次修改和排查的成本。

**来源：** 团队

### 发现就删 【必须】

发现后要处理，不当作“先留着”放过。与当前任务无关时，先列入汇报并询问，授权后用独立分支和 PR，见 [change-workflow.md](../collaboration/change-workflow.md)。

**来源：** 团队

### 删除前确认没有使用方 【必须】

用实际依据判断，不靠猜测：

1. 全局搜索引用，包括字符串形式的动态引用。
2. 检查配置、脚本、定时任务和 CI。
3. 涉及数据时，确认是否还有读取方。
4. 有疑问时，向用户确认。

既然没人读取，就不需要继续写入和保留。法定留存、审计和备份数据除外，这类数据按保存期限处理，见 [隐私](../backend/security/privacy.md)。

## 清理范围

| 类别 | 内容 |
|---|---|
| 代码 | 未调用的函数、死分支、已被替代的实现 |
| 开关 | 已完成切换的新旧开关 |
| 数据 | 没有读取方的字段、表和旧索引（法定留存、审计和备份数据除外） |
| 测试 | 产品代码中的 mock、不再使用的测试替身、过时的测试和测试数据 |
| 文档 | 过时文档和没有用途的文件 |
| 工程 | 没有必要的门禁检查和脚本 |
| 分支 | 已合并的分支 |
| 需求 | 不值得做的需求 |

### 替换完成后删除旧实现 【必须】

新实现上线后，开关、旧路径和旧测试一并删除。

**来源：** 团队

### 不值得做的需求连文档一起删 【必须】

决定不做时，把文档中的需求点一起删除，避免后续继续围绕它开发。

**来源：** 团队

### 破坏性数据操作先确认 【必须】

删除代码由版本控制兜底，删除线上数据无法用同样方式恢复。删除生产数据或不可恢复的内容前，先向用户确认。
