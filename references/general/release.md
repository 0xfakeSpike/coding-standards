# 发布与回滚

## 发布

**适用：** 线上服务（本节全部规则）

发布内容能按构建标识复现，见 [dependencies.md](dependencies.md) 的“构建可复现”和 [ci-cd.md](ci-cd.md) 的“构建可追溯”。

### 按风险分阶段发布 【推荐】

高风险改动先小范围发布，确认指标正常后再扩大。

| 方式 | 适用场景 |
|---|---|
| 灰度 | 逐步放量，观察影响 |
| 蓝绿 | 需要快速切换和回退 |
| 滚动 | 常规无状态服务更新 |

**来源：** Google SRE 发布工程

### 发布前写清步骤 【必须】

| 项目 | 内容 |
|---|---|
| 变更范围 | 这次发布包含什么 |
| 发布顺序 | 数据库、配置和服务的先后顺序 |
| 观察指标 | 判断是否正常的指标 |
| 回滚方式 | 触发条件和具体步骤 |

### 修复优先进入主干 【推荐】

发布分支需要修复时，先修主干，再 cherry-pick 到发布分支，避免下个版本丢失修复。

**来源：** Google SRE 发布工程

## 功能开关

### 按类型管理 【推荐】

| 类型 | 用途 | 生命周期 |
|---|---|---|
| Release | 隐藏未完成功能 | 短期 |
| Experiment | A/B 实验 | 实验期内 |
| Ops | 运行时保护 | 按需保留 |
| Permissioning | 按用户开放 | 可长期 |

**来源：** Fowler 功能开关

### 开关要有负责人和清理安排 【必须】

Release 和 Experiment 开关要有负责人和删除日期，切换完成后，开关和旧路径一起删除。Ops 和 Permissioning 开关要有负责人和定期复核日期。

**来源：** 团队、Fowler 功能开关

### 决策逻辑集中 【推荐】

开关判断收敛到一处，不在代码中散落 `if`。

**来源：** Fowler 功能开关

## 回滚

**适用：** 线上服务（本节全部规则）

### 回滚要提前准备 【必须】

上线前确认回滚步骤可行。

### 事故时先止损 【必须】

先恢复服务，再分析根因。止损手段完成后，仍要根本修复。
