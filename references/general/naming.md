# 命名原则

本文只讲语言无关的原则。大小写和具体格式见语言层。

### 一眼看出含义 【必须】

读者不看实现也能知道用途。

| 不推荐 | 推荐 |
|---|---|
| `data` | `pendingOrders` |
| `flag` | `isExpired` |
| `process()` | `calculateInvoiceTotal()` |

**来源：** 团队

### 映射类变量写明 key 【必须】

名字要说明通过什么查找什么。

| 不推荐 | 推荐 |
|---|---|
| `users` | `userById` |
| `cache` | `priceBySku` |

**来源：** 团队

### 同一概念用同一个词 【推荐】

不混用多个词指同一实体，也不用同一个词表达不同概念。业务术语容易混淆时，在项目文档中维护术语表。

**原因：** 词不统一时，搜索和理解成本都会上升。

### 名字随职责更新 【必须】

职责变化后，名字要同步修改，不留下过时的名字。

**来源：** 团队

### 遵守语言习惯 【推荐】

不把一种语言的命名风格带到另一种语言。

### 词性约定 【推荐】

| 对象 | 约定 |
|---|---|
| 函数 | 动词或动宾结构 |
| 类型 | 名词 |
| 布尔值 | 能回答“是或否”的表达 |
| 集合 | 复数或带集合含义 |

### 反义词成对使用 【推荐】

| 成对词 |
|---|
| `start` / `stop` |
| `open` / `close` |
| `add` / `remove` |
| `create` / `delete` |
| `begin` / `end` |
| `enable` / `disable` |

### 单位要明确 【推荐】

优先用类型表达单位，比如时长类型。类型无法表达时，在名字中写明单位，比如 `timeoutMs`。

### 名字长度与作用域匹配 【推荐】

作用域越大，名字越完整。几行内的局部变量可以简短。

### 缩写要通用 【推荐】

只使用行业通用缩写，比如 `id`、`url`、`http`。业务缩写要在项目文档中说明。

## 命名坏味道

| 坏味道 | 问题 |
|---|---|
| `data`、`info`、`temp` | 没有信息量 |
| `manager`、`helper`，或把业务逻辑放进 `utils` | 职责不清 |
| 用 `newXxx`、`xxx2` 区分新旧实现（不含构造函数） | 名字没有说明差异 |
| `handleData` | 动作和对象都含糊 |
| 否定布尔值，如 `isNotReady` | 判断时出现双重否定 |
