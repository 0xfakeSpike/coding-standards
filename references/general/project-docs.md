# 项目文档

代码中不写注释，因此项目文档是记录背景和注意事项的地方。

## 注意事项

### 记录代码无法表达的内容 【必须】

包括业务背景、设计权衡、外部系统限制和非直觉的行为。放在哪里、怎么组织由项目决定，写清要注意什么和为什么。

**来源：** 团队

### 文档随代码更新 【推荐】

修改行为时同步更新文档，过时内容直接删除。

### 待办记入工单 【推荐】

没有工单系统时，集中记录在项目文档中。

## 对外文档

### 用词专业精炼 【必须】

不用口语化表达。

**来源：** 团队

## README

### README 回答上手问题 【推荐】

| 内容 | 说明 |
|---|---|
| 项目用途 | 一两句话说明 |
| 环境要求 | 语言、工具和版本 |
| 启动方式 | 可直接执行的命令 |
| 常用命令 | 测试、lint、构建 |
| 目录结构 | 主要模块的职责 |
| 文档入口 | 其他文档的位置 |

## 变更日志

### 需要时按 Keep a Changelog 维护 【推荐】

- 最新版本在前，每个版本写明日期，日期用 ISO 8601。
- 维护 `Unreleased` 区块。
- 按 Added、Changed、Deprecated、Removed、Fixed、Security 分组。

**来源：** Keep a Changelog

## 架构决策

### 重要决策写 ADR 【推荐】

一条 ADR 记录一个决策及其理由、权衡和后果。

```text
docs/adr/adr-001-short-title.md

# 标题
## 状态
## 背景
## 决策
## 后果
```

**来源：** Nygard ADR、ADR 站点

### ADR 编号递增且不复用 【推荐】

决策被推翻时，保留旧记录并标记为已被替代。ADR 是决策历史，不算过时文档。

**来源：** Nygard ADR

## 技术方案

### 方案先讲清核心问题 【推荐】

包括背景、目标、非目标、方案、取舍、风险和验证方式。

用户说“直接开发，不用写方案”时，不写方案。

**来源：** 团队

## 运维手册

### 线上服务提供运维手册 【推荐】

写清部署方式、关键指标、常见故障和处理步骤。
