# 代码设计

## 架构与合理性

### 架构决定简洁程度 【必须】

代码是否简洁，首先取决于架构是否合理，而不是事后清理。设计时优先考虑概念和职责是否清楚。

**来源：** 团队

### 能跑不等于合理 【必须】

系统能工作，但概念别扭，也要改。

**判断信号：**

- 需要额外解释才能说清为什么这样设计。
- 同一概念在不同模块中含义不同。
- 新需求总要绕过现有结构。

**来源：** 团队

### 选最优位置 【必须】

评估改动最该放在哪里，不因为“现在这里能做”就做在这里。

**判断问题：**

1. 这件事属于哪个模块的职责？
2. 放在这里，会让哪个模块知道它不该知道的事？
3. 同类逻辑现在放在哪里？

**来源：** 团队

## 抽象

### 不做没有必要的封装 【必须】

只转调一次的函数、只包一层的结构，都不要保留。

**原因：** 每层封装都要读者多跳转一次，却没有增加信息。

**判断标准：** 封装应当隐藏复杂度、统一规则或表达概念。三者都不满足就删除。

**来源：** 团队

### 组合优先于继承 【推荐】

继承会让子类依赖父类的实现细节。需要复用行为时优先用组合。

### 不提前抽象 【推荐】

出现真实的第二个或第三个使用方时再抽象。

**来源：** Fowler YAGNI

### 不为模式而模式 【推荐】

设计模式用来解决已经出现的问题，不用来证明设计“规范”。模式增加的间接层要有实际收益。

## 依赖

### 依赖方向单向 【推荐】

模块之间不出现循环依赖。确实需要替换实现时，高层业务才依赖抽象，不为此提前定义接口。

### 依赖外部传入 【推荐】

需要替换或测试的依赖由外部传入，不在业务逻辑中直接创建。

## 数据与副作用

### 副作用集中在边界 【推荐】

核心逻辑尽量写成纯函数，I/O 放在外层，这样逻辑才容易测试。

### 优先不可变数据 【推荐】

共享数据默认不修改。需要修改时，范围要小且明确。

## 设计原则速查

| 原则 | 含义 | 常见违反信号 |
|---|---|---|
| 单一职责 | 模块只有一个变化原因 | 文件什么都管 |
| 开闭 | 通过扩展增加行为 | 每加一种类型都改多处判断 |
| 里氏替换 | 子类型可替换父类型 | 子类抛出“不支持” |
| 接口隔离 | 使用方只依赖所需接口 | 实现大量空方法 |
| 依赖倒置 | 业务不依赖具体实现细节 | 业务层直接操作驱动 |

这些原则是判断工具，不是目标。为满足原则而增加层次时，要回到“不做没有必要的封装”重新判断。

## 常见反模式

| 反模式 | 表现 | 处理 |
|---|---|---|
| 上帝对象 | 一个模块承担大量职责 | 按职责拆分 |
| 贫血的壳 | 类型只是转调另一个类型 | 删除这一层 |
| 霰弹式修改 | 一个需求要改很多文件 | 收敛重复逻辑 |
| 特性依恋 | 函数大量读取其他模块的数据 | 把逻辑移到数据所在位置 |
| 布尔参数分支 | 一个函数靠标志做两件事 | 拆成两个函数 |
