# 前端架构

本文写目录与模块边界、渲染模式、monorepo、微前端和设计系统。组件内部设计见 [components.md](components.md)，语言无关的职能规则见 [responsibilities.md](../general/responsibilities.md)。

## 目录与模块边界

### 职责和层次要清楚 【必须】

每个目录、模块和组件都要能说清属于哪一层、负责什么。路由入口只组装页面，功能模块负责业务流程，通用层不含业务知识。

**原因：** 层次混在一起后，一处改动会牵连多处，也无法判断新代码该放在哪里。

**来源：** 团队

### 按业务功能组织代码 【推荐】

一个功能的组件、逻辑、请求和类型放在一起，不按文件类型把它们分散到全局目录。Vue 项目用 `composables/` 代替 `hooks/`。

```text
src/
├── app/
├── features/
│   └── order/
│       ├── components/
│       ├── hooks/
│       ├── api.ts
│       └── types.ts
├── components/
├── hooks/
├── lib/
└── utils/
```

| 目录 | 内容 |
|---|---|
| `app/` 或 `pages/` | 路由入口 |
| `features/` | 业务功能 |
| `components/`、`hooks/` | 跨功能的通用 UI 和逻辑 |
| `lib/` | 请求客户端、第三方封装 |
| `utils/` | 无业务含义的纯函数 |

**原因：** 修改一个功能时不用跨多个目录，删除功能时也能整体移除。

### 依赖方向保持单向 【推荐】

路由入口可以依赖 `features`，`features` 可以依赖 `components`、`lib`、`utils`，反方向不行。功能之间的依赖走下一条的公开入口。通用层不能导入业务模块。

**原因：** 反向依赖会让通用代码带上业务知识，也容易形成循环依赖。

**工具：** ESLint `no-restricted-imports`。Nuxt 的自动导入不经过 `import` 语句，这个检查覆盖不到，目录做法见 [nuxt.md](nuxt.md)。

### 功能之间只走公开入口 【推荐】

一个功能使用另一个功能时，只导入对方明确公开的模块，比如 `@/features/order`，不深入 `@/features/order/components/table/format` 这样的内部文件。入口文件逐个列出导出，不用 `export *`。

**原因：** 内部文件一旦被外部引用，就无法自由重构。

### 同一件事只留一份 【必须】

日期格式、金额格式、断点常量、请求客户端这类同一件事，全项目只保留一份实现。比如日期都调用同一个 `formatDate`，不在各处分别写格式字符串。

**原因：** 多份实现迟早行为不一致，修改时也容易漏掉。

**来源：** 团队

## 渲染模式

### 按页面选择渲染模式 【推荐】

先测量瓶颈再选择，优先考虑静态或服务端渲染。同一站点可以按页面混用。

| 模式 | 适合 | 代价 |
|---|---|---|
| CSR | 登录后的强交互应用 | 首屏依赖 JavaScript，搜索引擎收录需要额外验证 |
| SSR | 内容随请求变化且要求首屏快 | 消耗服务器算力，首字节时间可能变长，需要考虑缓存 |
| SSG | 内容在构建时确定 | 所有 URL 要提前可知，不适合海量或个性化页面 |
| ISR | 内容量大、允许短暂过期 | 依赖框架和部署平台，要定义失效策略 |

**来源：** web.dev 渲染方案、Next.js 文档、Nuxt 文档

### 内容型页面不用纯客户端渲染 【推荐】

首屏速度或搜索收录重要的页面，用 SSR 或 SSG 输出完整 HTML。

**原因：** 纯 CSR 要等 JavaScript 下载执行后才有内容。SSR 也要控制客户端代码量，否则页面看起来就绪却无法响应操作。

**例外：** 登录后才能访问的后台和工具类页面。

**来源：** web.dev 渲染方案、Vue 文档

### 服务端不共享模块级可变状态 【必须】

服务端渲染时，模块只初始化一次并被所有请求复用。用户相关状态必须按请求创建，不能放在模块级变量里。

**原因：** 模块级状态会把一个用户的数据泄漏给另一个用户。

**来源：** Vue 文档、Nuxt 文档

### 服务端和客户端的首次渲染结果一致 【必须】

使用服务端渲染时，`window`、`localStorage` 这类浏览器 API 只在挂载后或客户端专用代码中访问。随机数、当前时间和本地时区不能让两端渲染出不同内容，响应式差异优先用 CSS 媒体查询处理。

**原因：** 水合不匹配会带来额外性能开销和错误的界面。

**来源：** Vue 文档、Nuxt 文档

## Monorepo

### 应用和共享包分开放 【推荐】

`apps/` 放应用和服务，`packages/` 放共享库和工具配置。包不要嵌套在另一个包里。

**来源：** Turborepo 文档

### 依赖装在使用它的包里 【推荐】

每个包的 `package.json` 列全自己用到的依赖。根目录只放管理仓库的工具。

**原因：** 依赖关系清楚，各包的构建缓存和裁剪也才准确。

**来源：** Turborepo 文档

工作区、内部依赖和跨包导入见 [project.md](../languages/typescript/project.md)。

### 构建任务声明依赖和产物 【推荐】

用 `dependsOn: ["^build"]` 保证依赖包先构建，用 `outputs` 声明产物，否则 Turborepo 不缓存任何文件。部署这类有副作用的任务关闭缓存。

**来源：** Turborepo 文档

## 微前端

### 默认不用微前端 【推荐】

只有多个团队确实需要独立开发和独立部署时才采用，并在运行时集成，不在构建时把子应用合并成依赖包。子应用之间只通过 URL、自定义事件或容器传入的回调通信，状态和样式相互隔离。

**原因：** 它会带来重复依赖、环境差异和更多运维工作，构建时集成还要求同步发布，失去独立部署的意义。

**来源：** Fowler 微前端

## 设计系统

视觉值的规则见 [css.md](css.md)。

### 共享库只放通用 UI，验证后再抽取 【推荐】

设计系统只收录图标、按钮、输入框这类没有业务含义的组件。先在功能内实现，出现真实重复且接口稳定后再抽取。

**原因：** 过早抽取时很难猜对 API，业务组件进入共享库后会耦合所有使用方。

**来源：** Fowler 微前端
